## Project overview

`not-so-jarvis` is a local AI assistant dashboard ("JARVIS") built with **plain Node.js** (no framework, zero npm dependencies) and **vanilla HTML/CSS/JS** (no bundler). It runs entirely on the user's machine with no cloud dependency. It provides:

- Chat with local AI providers (Ollama)
- System monitoring widgets (CPU, RAM, VRAM/GPU)
- A model library with hardware-compatibility detection
- AI image generation via a local ComfyUI instance using the **Krea2** text-to-image workflow

Version 0.1.0, MIT license. Entry point is `server.js`.

## Purpose of each important directory

- **`server/`** — Server-side application logic. These modules are required by `server.js` and do the actual work: chat, conversations, providers, config, model catalog.
- **`services/`** — Cross-cutting / independent services. `image-generator.js`, `comfyui.js`, and `vram-manager.js` together form the image generation pipeline. `director/` orchestrates Director Mode productions and `long-video/` orchestrates >15s videos. `system-monitor.js` provides telemetry, and `weather.js` provides server-side weather lookups for chat. `news.js` parses keyless RSS/Atom feeds for the NEWS widget and chat context. `generated-history.js` persists image metadata and `thumbnail.js` mints the gallery's cached low-res PNG thumbs in the background.
- **`public/`** — Everything served to the browser. `app.js` is the main entry; `public/js/*` are feature modules loaded as plain scripts (no modules/bundler).
- **`data/`** — Runtime persistence. JSON files are the source of truth for config/conversations/history; generated images land in `data/generated/`.

## Important services and integrations

- **Ollama** (`http://localhost:11434`) — chat provider via `server/providers.js`.
- **ComfyUI** (`http://127.0.0.1:8188`, overridable via `COMFYUI_URL`) — image generation via `services/comfyui.js`. Raw ComfyUI failures are classified (`classifyComfyError`) into stable codes (`comfyui_oom`/`comfyui_missing_model`/`comfyui_missing_node`/`comfyui_validation_error`) with actionable hints, and idempotent reads (`getObjectInfo`, `downloadImage`, `/history` polling) use bounded `withRetry` backoff for transient unreachable/5xx errors.
- **ComfyUI launcher** — `services/comfyui-launcher.js` starts a local ComfyUI server as a detached background process when it is offline. Resolution order: an explicit `COMFYUI_START_CMD` (env) or `comfyui.startCommand` (config) override, then ComfyUI Desktop (`installations.json` under the Electron userData dir, launching the standalone install's venv python + `main.py` headless), then a portable/venv layout (sibling `run_nvidia_gpu.bat`/`run_cpu.bat` or a resolved python). `comfyui.root` is cached in `data/config.json` when detected so a launch still works while ComfyUI is offline. `start()` is idempotent and single-flight, writes logs to `data/comfyui-start.log`, and polls `isAvailable()` until `COMFYUI_START_TIMEOUT_MS` (default 180s). Exposed by `POST /api/comfyui/start` (widget Start button) and the deterministic `isStartComfyRequest` chat gate in `handleChatStream` (so a "start comfyui" message never falls through to the chat model). `GET /api/comfyui/status` reports `canStart`/`startMethod` when offline.
- **Krea2 workflow** — assembled in `services/image-generator.js` (`buildKrea2T2IGraph`), using UNET/CLIP/VAE models configured through settings or env vars (`KREA2_*` in `.env.example`).
- **Qwen Image 2.1 workflow** — assembled in `services/image-generator.js` (`buildQwenImage21T2IGraph`), the alternate text-to-image pipeline selected by `imageGeneration.model` (`qwen_image_2_1`). Uses UNETLoader/CLIPLoader (`qwen_image`)/VAELoader with the `TextEncodeQwenImage21` core node and `EmptyLatentImage`; files come from `Comfy-Org/Qwen-Image-2.1` (env `QWEN_IMAGE_*` in `.env.example`). Downloaded by the Setup guide only when the model is selected.
- **Long Video Director** — `services/long-video/*` owns videos longer than H3's 15-second ceiling. The **duration router** (`director.isLongVideoRequest`, raw `parseRequestedSeconds`) sends >15s video requests to the Long Video Director and leaves <=15s on the existing H3 workflow untouched. The director builds a **Story Bible** (`plan.js` `data/long-video-state.json`) and a **beat plan** (one beat per shot, each <=15s, fewest beats possible; `prompts.segmentDuration` matches the documented splits 20→10+10, 25→13+12, 30→15+15, 40→13+14+13, 60→15×4), composes the paragraph-based prompt (paragraph 1 = scene, every later paragraph = one beat; **no `[Shot N]`**), and shows the storyboard once for approval. Approval submits **one** ComfyUI job to the installed `Smite79/MiniMax-H3-LongVideos` node (`H3LongVideos`), which performs the temporal chaining internally; `generator.js` never extracts a frame and never concatenates clips. `h3-longvideos-workflow.js` builds/validates the graph from the swappable config `workflows/h3-longvideos.json`, so the underlying ComfyUI workflow can change without touching the director. Contextual edits (`applyStoryboardUpdate`) rewrite the Story Bible and affected beats, never append to the old prompt. The plan/approval UI is `public/js/long-video.js` (`LongVideoUI`) with the persisted `[[longvideo:{...}]]` marker, `GET /api/longvideo/state`, and the `body.longVideoAction` button payload (`approve`/`modify_plan`/`retry`/`cancel`). Env: `H3_LONGVIDEO_MAX_SECONDS` / `H3_LONGVIDEO_STEPS` / `H3_LONGVIDEO_TIMEOUT_MS`.
- **Long Video motion continuity** — `services/long-video/motion.js` owns explicit motion/world-state continuity so beats don't behave like independent clips. Every beat carries an `ending_motion_state` (camera movement/direction/speed/momentum/orientation/framing/screenPosition, subject movement/direction/speed/pose/gaze/hands, moving objects, environmental movement) and an `ending_world_state` (clothing/appearance/location/props/objectStates/completedActions); every beat after the first carries `transition_from_previous` (`initial_continuation` → `transition` → `new_action` → `resulting_motion_state`). `motion.reconcileMotionChain()` runs after every plan/build/update: it normalizes states, carries world state forward (completed actions and object states are never re-executed), and **fills/repairs** each transition from the previous beat's actual ending state — continue → decelerate/reverse/settle → new motion (pan→push-in passes through "the pan settles, then a gentle push in begins"; reversals pass through "carries its pan briefly, gradually slows, then smoothly reverses"). Planner-provided transitions are preserved; gaps are filled deterministically. `transition_mode` is `continuous_transition` (default) or `abrupt_transition`, auto-detected from cut/jump/sudden wording. `composeLongVideoPrompt` writes these as plain cinematic prose — schema field names are never sent to H3. Because the LongVideos node renders all beats in ONE job, the ending states are planned (not observed from generated frames); the node still owns the actual frame-to-frame conditioning.
- **UGC Studio** — `services/ugc/*` is a chat-first workflow layer (not a separate dashboard). A UGC request ("create a UGC video for my product", "make a TikTok ad", "write me a UGC script") is caught by a deterministic gate in `server.js` `handleChatStream` *before* the Long Video/Director gates and the task router, so a brief never becomes a normal image/video generation and a >15s UGC request is not captured by the duration router. `studio.detectUgcIntent` (noun + action) drives it; the project stage is tracked by the application, not the LLM. Stages: `brief` → `product_selection` → `creator_selection` → `creative_direction` (content type + outfit + environment) → `script_review` → `scene_review` → `reference_generation` → `reference_approval` → `video_generation` → `completed`. Each stage renders an inline card carried by a persisted `[[ugc:{...}]]` marker (stripped from model context in `context-builder.js`); actions arrive as `body.ugcAction` and typed follow-ups are classified by `studio.classifyMessage` (conservative — unrelated requests fall through to the normal router). Projects persist to `data/ugc-state.json` (`GET /api/ugc/state`); exiting keeps a draft (`status: draft`) that resume reactivates. Product Library (`data/ugc-products.json`, `GET/POST /api/ugc/products`, `DELETE /api/ugc/products/:id`) stores only user-supplied facts — never invented claims. Script/scene generation use the chat LLM with facts-only system prompts and deterministic fallbacks (`prompts.js`); scene durations are always fitted to the requested total (`studio.fitDurations`). Dialogue is always fitted to a natural speaking pace: `prompts.SPEAKING_WORDS_PER_SECOND` (≈2.3) + `prompts.dialogueWordBudget`/`fitDialogueToBudget` cap each scene's line to its duration (a 5s cut carries ~11 words), `prompts.enforceDialogueBudgets` runs in `studio.save()` so no path can persist an over-long line, and the script/scene/regenerate prompts carry an explicit word budget (an over-long line is delivered too fast and sounds robotic). Continuity (`studio.reconcileContinuity`) pins creator/outfit/environment across scenes. Reference frames reuse the image pipeline (`studio.buildReferenceRequest` → `imageGenerator.buildImagePrompt` → `imageGenerator.generateImage`) and are recorded in the gallery. The approved project hands off to the existing Director Mode via `director.createUgcProduction`: the UGC scene plan becomes the Director brief's `shotList` (structured, never a text blob) and **every approved scene reference frame** travels with the production (`production.references`); the Director's video stage conditions H3 on all of them via the core `MiniMaxH3ReferenceToVideo` node (reference-to-video, addressed as `<Picture 1..N>`, `videoMode: 'ref2va'`), instead of animating only a single opening frame; each scene's `dialogue` is carried into that `shotList` as an on-screen `(S1)`/`<d>[English] …</d>` line (never a raw `script:` blob in `details`, which H3 read as voiceover and left the mouth closed), and the deterministic scene fallback distributes the approved script across scenes (`prompts.distributeDialogue`) so a failed scene LLM still speaks on camera; the spoken language (default English, or a named language in the request via `prompts.dialogueLanguageFor`) is written into the `<d>[Language]` tag and the approved line is re-asserted deterministically by `videoGenerator.ensureShotDialogue` after the H3 director LLM, so a dropped dialogue block can never make H3 invent speech in its own language; `handleUGCDirectorHandoff` then runs the existing `runDirectorVideoStage`. The UI is `public/js/ugc.js` (`UGCUI`, loaded before `chat.js`) with the `.ugc-bar` "UGC Studio · Active" indicator and `.ugc-*` cards. Tests: `test/ugc.test.js`.
- **UGC Studio integrity rules** — `services/ugc/studio.js` owns a canonical brief schema (`BRIEF_FIELDS`: objective, productName, brand, productCategory, contentType, platform, duration, aspectRatio, targetAudience, tone, keyMessage, callToAction, environment, dialogueLanguage, creatorDescription, additionalInstructions) that must survive extraction, `mergeBrief`, normalization, save/reload and regeneration. Every server action is validated against the live stage by `studio.validateAction` (never trust the UI), stale cards are rejected by `studio.isStaleAction` (project `version`), and overlapping actions are serialized per conversation in `server.js`. References are fingerprinted by `studio.currentPlanHash` (visual fields only — scene id/order/duration/action/camera/productVisibility/environment/outfit, plus creator/outfit/environment/product/aspect/duration): any visual edit calls `studio.invalidateReferences` (clears `approvedReferences`, marks frames stale), `studio.approveReferences` requires exactly one current frame per scene (missing/stale/failed/duplicate reject), `studio.referencesComplete`/`pendingReferenceSceneIds` drive the UI, and `studio.recordReferenceFailure` preserves partial successes for retry-failed-only. Duration is bounded by `prompts.DURATION_LIMITS` (1–60s planned, 15s render ceiling): `prompts.validateDuration` validates edits, `studio.resizeScenesForDuration` recomputes scene count/durations, and a >15s brief is **never silently clamped** — the handoff explains the cap and requires an explicit `confirm_duration` ("continue at 15 seconds"). Creator-free (product-only) mode is explicit (`studio.skipCreator` → `creatorMode: 'none'`), and script/scene/reference/Director prompts never invent a person. LLM output is validated facts-only (`prompts.validateScript`/`validateScenes`: unsupported price/guarantee/certification/medical/result/superlative/personal-experience claims stripped and flagged `needsConfirmation`, usage verbs checked against `usageInstructions`, dialogue trimmed to budget, duplicate scene IDs repaired). Product reference images travel on a separate `product_references` channel (never merged with scene frames). A saved product can be removed from the library via the product card's delete action (`studio.deleteProduct`, validated like every other action; the project keeps its own snapshot, and `DELETE /api/ugc/products/:id` remains for direct API use). Lifecycle: `studio.syncDirectorOutcome` (matched by the existing `directorProductionId`) marks the linked project `completed` on Director success (so it stops intercepting chat) or returns it to `reference_approval` with `lastError` on failure/cancel. Tests: `test/ugc.test.js`.
- **Director Mode** — `services/director/*` coordinates video production. Video requests run through the normal H3 pipeline by default — there is no Direct-video-vs-Director-mode question. Director mode starts only when the user asks for it explicitly, either by typed phrasing (`director mode`, `as a director`, `wantsDirectorMode`) or the composer **Director Mode toggle** (`public/js/chat-director.js`, `#chatDirector`), which sends `body.forceDirector`; `director.shouldForceDirector(message, decision)` then routes a fresh video turn (`new_task`/`switch_task`) straight to the Director, while explicit "just generate the video" (`wantsDirectMode`) still wins and `continue_task` tweaks of an active video task are untouched. The toggle also **supersedes the long-video duration router**: `director.shouldForceDirectorOverLongVideo(message, { forceDirector, longVideoBusy })` lets a `>15s` request with the toggle on bypass the Long Video gate and start the Director instead (and any parked long-video storyboard is dropped so its approval can't capture the production), while explicit `wantsDirectMode` and an actively rendering long video still win. Because the Director's video stage is H3, a `>15s` toggle request is clamped to the 15s ceiling by `parseRequestedVideoDuration`. Choosing Director builds the canonical brief and runs opening image → approval checkpoint → H3 I2VA video. `buildVideoStageRequest` conditions the H3 video on the single approved opening frame (`i2va`), or, when the production carries `references` (the UGC handoff), on every approved scene frame at once (`ref2va`, addressed as `<Picture 1..N>` through the core `MiniMaxH3ReferenceToVideo` node). The canonical creative brief (`production-plan.js`, persisted to `data/director-state.json` per conversation) is the source of truth: a direction change updates the brief via `director-prompts.js` and rebuilds the image prompt, never appends to the old one. The brief has a free-form `details` catch-all (props, wardrobe, dialogue, named styles) so specifics survive the structured fields, and while `briefModified` is false the compose functions also carry the user's original wording as authoritative context for the image/H3 prompts. **Director productions are cut like a film, not one continuous take:** the brief carries an ordered `shotList` (planned by the brief LLM, with `director-prompts.planShots` as the deterministic fallback — roughly one cut per three seconds, capped at five, unless the user explicitly asks for a single take), `composeVideoDirection` translates it into a numbered shot plan, and `buildVideoStageRequest` passes `shot_plan`/`multi_shot` into `videoGenerator.buildH3VideoPrompt`. When a shot plan is present the H3 director switches to the `H3_MULTISHOT_ADDENDUM` (official guide cut syntax: `[Shot N] At 00:0S.SSS, the camera cuts to …`, strictly increasing, no timestamp on `[Shot 1]`), a rewrite with fewer than two `[Shot N]` markers is rejected and retried, and the deterministic `buildMultiShotFallbackPrompt` emits the plan even if every LLM step fails. The normal direct-video pipeline carries no shot plan and stays single-shot unless the user explicitly requests multiple shots. The Director decides WHAT runs; `image-generator.js`/`video-generator.js` decide HOW. **Spoken dialogue is on-screen speech, not narration:** the H3 director system prompt (`H3_DIRECTOR_SYSTEM_PROMPT`, also in the multishot addendum) teaches the official speaker/dialogue syntax — stable `(S1)`/`(S1,S2)` speaker IDs, the speaker named and on screen with their mouth described as visibly lip-synced while they speak, the exact words preserved verbatim inside `<d>[Language] …</d>` (never translated/rewritten/invented), off-screen voiceover only when the user explicitly asks for narration (then "lips remain completely closed"), and dialogue kept out of `overall_soundscape`. Director briefs carry spoken lines in the brief's `shotList` in that form so `composeVideoDirection`/`buildH3VideoPrompt` preserve them. The server executes stages through the existing `handleImageGenerationStream`/`handleVideoGenerationStream` by passing `opts.director` (those handlers emit a `director` SSE card instead of the normal `image`/`video` event, mark the production stage ready/failed, and stop at approval); the direct-video pipeline runs the normal H3 path. Actions arrive as `body.directorAction` on `/api/chat/stream` (button clicks) or as typed decisions (`approval-manager.js` `classifyMessage`); `GET /api/director/state?conversationId=` restores card interactivity after a reload. The approval card also offers **Upscale Frame** (`approval-manager.js` `UPSCALE_IMAGE`, typed "upscale the frame" included): `runDirectorUpscaleStage` runs the shared image upscaler (`imageGenerator.upscaleImage`, SeedVR2/Ultimate SD — the single UPSCALE settings) on the opening frame, then `director.markImageUpscaled` points `production.image` at the `_up_` file (keeping `upscaled`/`upscaledFrom`) while the production stays at the approval checkpoint, so `buildVideoStageRequest` animates the higher-resolution frame. A failed upscale is non-terminal (`markUpscaleFailed`): the original frame and the approval card stay usable.
- **VRAM manager** — `services/vram-manager.js` enforces "one side resident, always": Ollama and ComfyUI are never loaded at the same time, and there are **no memory-pressure thresholds** (a pre-action check can see a healthy machine while both footprints are already stacked — e.g. right after a generation evicted the chat model but ComfyUI still holds its weights). Before any chat work `freeVRAMBeforeChat` unloads ComfyUI models; `comfyui.queuePrompt` sets a residency flag (`comfyui.hasResidentModels`/`forgetResidentModels`) so it skips the round-trip when the app queued nothing. The free now runs at the **start of the chat turn, before `taskRouter.routeMessage`** (`server.js` `handleChatStream`) because routing and image/video prompt building both consult the Ollama model — waiting until the chat-reply branch would let both load during routing. Before any image/video generation `freeVRAMBeforeImage` unloads **every** model Ollama has loaded (discovered from `/api/ps` via `providerManager.getOllamaStatus`, with `rememberChatModel` as a fallback), so a model loaded outside the app or before a restart is still evicted. **No Ollama call may run after a ComfyUI job until ComfyUI is freed** — the post-generation confirmation (`taskRouter.buildSuccessReply`) is therefore called with `deterministic: true` in the image/video/edit handlers (template sentence, no LLM), because ComfyUI keeps its weights resident until the next turn's `freeVRAMBeforeChat`; invoking the summary LLM there reloads the GB-scale chat model on top of them and froze the machine. Eviction is **verified**: `keep_alive 0` only schedules the unload, so `waitForChatRelease` polls `/api/ps` until each model is actually gone (bounded by `JARVIS_MODEL_RELEASE_TIMEOUT_MS`, `JARVIS_MODEL_RELEASE_POLL_MS`) then holds `JARVIS_MODEL_RELEASE_SETTLE_MS` so the OS reclaims the RAM before ComfyUI loads — without it a still-resident llama-server stacked under the video model and froze the machine. The ComfyUI side (`freeVRAMBeforeChat`/`freeComfyModels`) holds the same settle after `/free`. Every wait is per-call overridable (`opts.policy`-free `{ timeoutMs, pollMs, settleMs }`) so tests stay fast. The tradeoff is deliberate: a generation unloads and reloads ComfyUI per image/video turn, because prompt building needs Ollama first. `reconcileOnStartup()` (called from `server.listen`) frees ComfyUI models left over from a previous process. Director stages go through `prepareDirectorLlm` before their interleaved Ollama planning calls and `freeComfyModels` at the end of a stage.
- **Open-Meteo weather** — `services/weather.js` fetches current conditions (no API key) for the browser-reported location. The dashboard widget POSTs its geolocation to `/api/weather/location`; the server persists it in `data/config.json` (`weather` key) and injects a gated snapshot into chat context. `GET /api/weather` returns the cached current conditions.
- **RSS news** — `services/news.js` fetches keyless RSS/Atom feeds (curated defaults: BBC World, NPR, Hacker News), parses them with a regex reader (`parseFeed`), and caches the merged items for 10 minutes. The NEWS widget polls `GET /api/news` with a `category` scope (`all`/`global`/`local`) and a segmented ALL/GLOBAL/LOCAL control; `POST /api/news/settings` persists the custom feed list and the `localArea` used by the `local` scope in `data/config.json` (`news` key, sanitized by `config-manager`), resetting feeds to defaults when sent empty. `GET /api/news?topic=…` uses keyless Google News RSS search, and the `local` scope searches the saved area (area + extracted topic). Chat injects a gated snapshot (`buildNewsContext`, `NEWS_QUERY_RE`), with scope from `newsScope` (`LOCAL_NEWS_RE`/`GLOBAL_NEWS_RE`) and a topic from `extractTopic`. Headlines are treated as untrusted data and always link out to the source.

## Chat environment context

- Both chat paths (`handleChat`, `handleChatStream`) call `buildEnvironmentContext(message)` before `contextBuilder.buildContext`, appending a system message with live telemetry (`contextBuilder.buildSystemStatsContext`, gated on `SYSTEM_QUERY_RE`), weather (`weather.buildWeatherContext`, gated on `WEATHER_QUERY_RE`), and news (`news.buildNewsContext`, gated on `NEWS_QUERY_RE`). The gates keep unrelated turns lean, and the prompts instruct the model to use only the supplied values and never invent numbers, a forecast, or headlines. Telemetry now includes GPU utilization (`system-monitor._readVRAM`).

## Important architectural patterns

- **No framework on either side.** Node `http` server + vanilla JS frontend. `server.js` has all routing defined as a sequence of path+method checks inside `handleAPI()`.
- **Service modules exported as plain objects** with named functions; no classes (except `system-monitor.js` which uses a class).
- **Persistence is simple JSON files** in `data/`, rewritten in full on mutation. No ORM/schema library.
- **Frontend mirrors backend persistence**: conversations are also stored client-side in IndexedDB (`public/js/db.js`) for UI durability.
- **Image generation idempotency/locking**: only one image generation at a time, enforced by `withGenerationLock` in `image-generator.js`.
- **Long Video Director / duration router** — `services/long-video/*` handles videos over H3's 15s ceiling. In `handleChatStream`, *after* the deterministic "start ComfyUI" gate and *before* the Director Mode gate, `longVideoDirector.isLongVideoRequest` routes >15s requests to `handleLongVideoStart` (plan + storyboard card) and `handleLongVideoAction` (approve/modify/retry/cancel). It is independent of Director Mode: <=15s requests never reach it, so the existing H3 workflow is unchanged. `motion.reconcileMotionChain()` keeps every beat's camera/subject motion and world state continuous across the chain (see "Long Video motion continuity"). The installed `H3LongVideos` node does the actual chaining — JARVIS builds one prompt and submits one job; it must never add FFmpeg last-frame extraction or per-clip concatenation.
- **UGC Studio gate** — runs in `handleChatStream` immediately after the deterministic "start ComfyUI" gate and *before* the Long Video/Director gates, the Playground gate, and the router. An explicit `body.ugcAction` executes a card action; a typed follow-up to an active project is classified by `studio.classifyMessage`; a new `detectUgcIntent` request starts a project. Unrelated turns fall through, so normal chat/image/video generation still works (and stays untouched when UGC is inactive). Exiting sets the project to `draft`; only `discard` removes it. UGC frames are built as creative direction and handed to `imageGenerator.buildImagePrompt` — the studio never builds the final Krea2 prompt.
- **Intent Resolver layer (primary decision-maker)** — `services/intent-resolver.js` sits between the user message and the action router: `User Message → Context Builder → Intent Resolver → Structured Intent → Action Router (task-router) → Action`. `resolveIntent()` combines the current message, a compact conversation context (`buildIntentContext`: last user request, last assistant action, last generated image/video, active prompt/generation, selected video mode), explicit wording, and regex signals (`collectSignals`) into a structured intent `{ intent, confidence, mode, referencesPreviousContext, referencedGenerationId, extractedRequest, subject, creative_mode, explicit_constraints }`. Intents: `chat`, `image_generation`, `video_generation`, `prompt_writing`, `prompt_ideation`, `modify_previous_generation` (+ `image_edit`/`image_upscale`/`video_upscale`). The **action is decided first; media words ("image", "video", "prompt", "portrait", "cinematic") are only subject/context** — "write me a prompt for an image" is `prompt_writing`, not `image_generation`. The resolver NEVER executes a tool; `task-router.decisionFromResolvedIntent()` maps the structured intent to the executable decision. `mode` (video) is inferred without asking: `director` only for explicit Director wording, `direct` for every other video request. Priority hierarchy: **A** explicit user action ("director mode", "write a prompt …") → **B** semantic LLM (final authority when ambiguous, temperature 0, malformed JSON retried once, **`think: false`** — every chat-path classifier call (resolver, `task-router.askRouter`/`buildSuccessReply`, `imageGenerator.detectIntent`, `videoGenerator.detectVideoIntent`) pins reasoning off so a hidden thinking pass never delays the turn or piles GPU load onto the reply) → **C** regex/keyword signals (evidence only) → **D** chat fallback. Context inheritance is conservative: `referencesPreviousContext` requires a clear reference ("this"/"that"/"her"/"the image"/"make it …"/"change …"), so an unrelated new request never inherits the previous generation. Set `JARVIS_INTENT_DEBUG=1` (or pass `{ debug: true }`) to print the resolver decision, the regex evidence, and the final action.
- **Pending clarification state** — removed: video requests no longer ask Direct-video vs Director-mode. See "Director Mode" for the explicit trigger.
- **Two-level intent detection** (still used as signal evidence / fallback in `services/image-generator.js` and `services/video-generator.js`): a fast Level 1 regex SIGNAL (`imageRequestStrength` → `definite`/`likely`/`null`) decides whether the resolver's LLM is consulted; the structured LLM JSON is the final authority on tool execution, the chat model's free-text reply never is. The signal is **not** position-dependent (generation verbs can appear anywhere) and `isConceptQuestion` keeps "What is image generation?"-style questions as chat. Deterministic gates in `task-router.js` (`decisionFromResolvedIntent` excepted) remain only as narrow fallbacks; all classification runs at temperature 0.
- **Extended intent schema**: `detectIntent`/`IMAGE_INTENT_SYSTEM_PROMPT` return/expect `action` (`generate`|`modify`), `creative_mode` (`none`|`light`|`full`), `explicit_constraints`, and chat `related_task`. The resolver mirrors those fields. `CREATIVE_FREEDOM_RE` (exported from `image-generator.js`) detects "be creative"/"surprise me"; a creative request with no subject gets `DEFAULT_CREATIVE_PROMPT`. These fields flow to `buildImagePrompt` and into the ActiveTask `parameters`.
- **SSE streaming** for chat (`/api/chat/stream`) — `queued`/`generating` status, live ComfyUI `progress` (step %), text chunks, `stats`, then a final `done` event; image/video generations emit a single `image`/`video` event. Streamed text is **rendered throttled**: `public/js/chat.js` coalesces chunks into at most one markdown render every ~80ms (trailing edge) and skips the heavy DOM passes (`collapseUpscalePairs`/`VideoPlayer.scan`/card attach) until the final `done`, so a long reply can't saturate the main thread. A running job is cancellable: each `generation-queue` entry owns an `AbortController`, its `signal` is threaded through `withGenerationLock` into `comfyui.waitForPrompt`, and `cancelActive`/`POST /api/queue/cancel {active:true}` aborts the wait and interrupts ComfyUI.
- **Restart mechanism**: `POST /api/restart` exits with code `100`, which `start.bat` (Windows) / `start.sh` (macOS/Linux) catches to relaunch in the same terminal. Both launchers preflight for Node.js and offer to install it via `install-node.ps1` (winget → official MSI) or `install-node.sh` (brew/apt/dnf/pacman → official tarball) when missing.

## State-management patterns

- **Server config**: `data/config.json`, managed by `server/config-manager.js` (`getConfig`, `setModelConfig`, `getImageSettings`, `setImageSettings`). The `imageGeneration` key stores global image settings overrides (model, unet, clip, vae, qwenUnet, qwenClip, qwenVae, aspectRatio, imageSize, steps, cfg, qwenSteps, qwenCfg, seedMode, seed, variations, loras; width/height are derived from aspectRatio + imageSize via `resolveDimensions`). Steps/CFG are model-scoped: Krea 2 reads `steps`/`cfg`, Qwen Image 2.1 reads `qwenSteps`/`qwenCfg` (Settings > Image SAMPLING repaints the right pair when the model changes; double-clicking an input resets it to that model's default). `model` selects the active text-to-image pipeline (`krea2` default or `qwen_image_2_1`); `effectiveSettings()` merges defaults with stored overrides, and `resolveBaseModels()` maps the active model to its UNET/CLIP/VAE slots. `seedMode: 'fixed'` + `seed` makes generations reproducible, and `variations` (1–4) emits that many images per request at seed, seed+1, …; the seed used is recorded in generated-history metadata.
- **Conversations/messages**: `data/conversations.json`, managed by `server/conversation-service.js`. In-memory cache reloaded at startup. A conversation may be flagged `private` (locked) via `PATCH /api/conversations/:id { private }`; the flag hides its generated media from the shared gallery.
- **Generated media privacy**: image/video metadata entries store the originating `conversationId` (`generated-history.add`). `generatedHistory.listPublic()` drops entries whose conversation is private and backs `GET /api/generated` (the gallery widget, View All, and `@` picker); internal lookups (`list`) stay unfiltered so deletes/upscale pairing still work. Private origins are also skipped by the ACTIVITY log.
- **Active task state**: `data/task-state.json`, managed by `services/task-state.js`. Per-conversation task context (type, prompt, generatedAsset, parameters), reloaded at startup.
- **Generated image metadata**: `data/generated-history.json`, managed by `services/generated-history.js` (cached in memory, flushed on change).
- **LoRA stack**: part of global image settings (`imageGeneration.loras`). Each entry is `{ name, strength, on, triggerWord }`. Trigger words from active LoRAs are prepended to the image prompt at generation time.
- **Frontend settings**: `localStorage` for widget visibility and device settings; IndexedDB for conversations/messages. The last opened conversation is persisted under `jarvis-last-conversation` (managed by `conversations.js`) and reopened on boot by `renderActiveChat` in `app.js`, falling back to the newest conversation if it no longer exists.

The **Lifestyle & Candid theme must never determine a character's ethnicity, age or gender**, and the identity generator must never emit outfit/scene/social-media wording. `identity` lock always means "the current person stays the same"; changing a profile control explicitly is the only thing that invalidates an identity on its own, and a scene-only change must never regenerate the character. Generated people are always fictional — never name or resemble a real celebrity. `listProfileOptions()` feeds the UI; appearance categories are broad demographic regions, not single nationalities.

Keep every scene's dialogue inside the speaking-rate budget (`prompts.dialogueWordBudget`/`fitDialogueToBudget`, ≈2.3 words per second); a line longer than its shot can hold is spoken too fast and sounds robotic.

A locked outfit always wins — only the pack metadata is recorded. `custom` carries a user-defined outfit verbatim. Context wording selects a pack via `outfitPacks.detectOutfitPackFromText` (gym / beach / office / night out / lounge / edgy …), including typed follow-ups classified by `concept.interpretContextMessage`; naming exact clothing becomes a custom pack. Packs persist on character presets (`character-presets.js` `outfitPack`/`outfitPackCustom`) and the catalog is served by `GET /api/playground/outfits`. Tests: `test/outfit-packs.test.js`.

The concept is displayed as a persisted `[[playground:{...}]]` card (actions: Generate Image / Surprise Me Again / Modify Concept / Save Concept / Save as Character / Use as Chat Context). Actions arrive as `body.playgroundAction` on `/api/chat/stream` (`surprise`/`again`/`modify`/`generate`/`save`/`use_context`) and typed follow-ups are interpreted by `concept.interpretContextMessage` ("try another one" → re-roll same character/settings; "keep the outfit but make it a beach scene" → add the outfit lock + change only the environment) while the concept is an untouched preview. ## Important relationships between components

- **Chat → Image**: In `handleChatStream`, `task-router.routeMessage()` first runs the Intent Resolver (`intent-resolver.resolveIntent`: message + context + signals → structured intent) and maps that intent to an executable decision, then falls back to its own deterministic gates. Only when the decision says `shouldExecuteTool` does the app build a prompt, free VRAM via `vram-manager.freeVRAMBeforeImage()`, and run the pipeline. Otherwise it streams a normal chat reply (after `freeVRAMBeforeChat()`). Prompt meta-requests (`prompt_writing`/`prompt_ideation`) and chat never execute a tool. The router knows three image outcomes: `image_generation` (new T2I), `image_edit` (attached upload, explicit "edit this image", or content-targeted phrasing like "replace X with Y" / "swap X for Y" / "change X into Y" / "remove X" → edit of the upload/latest output via the Qwen editor), and `continue_task`/`modify` (always executed as a full-regen of the rewritten prompt; edits only run for explicit `image_edit`). Deterministic falls back on narrow, explicit intents so small chat models can't downgrade them to chat: upscale (incl. typo-tolerant matching), bare-`again` regenerates, anaphoric `another image`/`one more image` (always a new `image_generation` execution, rebased onto the image lineage by `resolveAnotherImageConcept`), and explicit new-phrasing requests (`isExplicitNewImageRequest` / `VIDEO_REQUEST_RE` — a generation verb driving at a media noun naming a subject). Tweaks, questions, and display requests keep flowing through the resolver/router.
- **Director gate**: in `handleChatStream`, before `taskRouter.routeMessage`, an explicit `body.directorAction` executes a card action, a typed decision matching the open production is classified by `approval-manager.classifyMessage`, and explicit `director mode` phrasing starts a Director production. Every other video request is no longer gated: the Intent Resolver returns `video_generation` with `mode: "direct"` and the normal H3 pipeline runs. A `body.forceDirector` flag from the composer Director Mode toggle hands any fresh `video_generation` decision to `handleDirectorStart` via `director.shouldForceDirector`, bypassing the direct pipeline. When the toggle is on, `director.shouldForceDirectorOverLongVideo` suppresses the Long Video gate first, so a `>15s` request reaches this branch instead of the duration router (a parked long-video plan is removed); `wantsDirectMode` and an actively rendering long video still take precedence. An open production never blocks normal chat: unrelated turns keep flowing through the router.
- **Creative Playground gate**: runs in `handleChatStream` *after* the Director gate and *before* the router/`freeVRAMBeforeChat`. An explicit `body.playgroundAction` (popover Surprise, or a card button) is executed by `handlePlaygroundAction`; a typed follow-up to an untouched preview is classified by `playground.classifyMessage` and enters the same handler. Concept assembly (again/modify/save/use-as-context) is deterministic (no model loads); a new **random character** additionally pre-renders its face via `runPlaygroundFaceStage` (frees VRAM, `buildImagePrompt`, `generateImage`, then `setCharacterImage`) before the card is emitted, failing open. Generate frees VRAM, runs `imageGenerator.buildImagePrompt` on `playground.buildImageRequest`, then `handleImageGenerationStream`. A concept that has been saved/used is no longer "open", so typed follow-ups flow to the normal router and never shadow an active image task.
- **Long video gate**: runs in `handleChatStream` *before* the Director gate (and before the router). An explicit `body.longVideoAction` executes a storyboard action; a typed decision on an open plan is classified by `longVideoDirector.classifyMessage`; a `>15s` video request (`isLongVideoRequest`, raw `parseRequestedSeconds`) starts the Long Video Director and stops at the storyboard approval card. It never reaches the <=15s H3 pipeline. The one exception is the composer Director Mode toggle: with `body.forceDirector` on (`shouldForceDirectorOverLongVideo`, explicit "just generate the video" and an active render still excepted) a `>15s` request bypasses this gate and is handled by the Director above. While a long video is actively rendering, only cancel is honored by the gate — a fresh request flows to the normal router so the running plan state is never clobbered.
- **ActiveTask lifecycle**: per-conversation task state lives in `services/task-state.js` (typed as `image`/`video`/`audio`), persisted to `data/task-state.json`. It stays active across turns and survives server restarts. It is only cleared when the user starts a different non-tool task or the application clears it. Tool execution sets `status: running` before running and `completed`/`failed` only after the tool actually finishes. The task also keeps `lastImage` lineage (prompt, original concept, creative mode) across video tasks so anaphoric requests like "generate me another image" and pronoun upscales rebase onto the image style, never the H3 video prompt; vague lineage prompts ("an image") are skipped in favor of the last concrete one.
- **Image pipeline**: `generateImage()` reads global settings (`effectiveSettings`), prepends active LoRA trigger words to the prompt, builds the Krea2 graph, validates against ComfyUI's object info, queues it, waits, downloads the output, saves to `data/generated/`, and records metadata in `generated-history`.
- **Config flow**: Settings UI → `POST /api/settings/image` → `imageGenerator.saveSettings` → `sanitizeSettings`/`sanitizeLoras` → `config-manager.setImageSettings` → `data/config.json`. At generation time `effectiveSettings()` merges defaults with stored overrides.
- **VRAM orchestration**: `vram-manager` connects chat providers and ComfyUI, unloading whichever model isn't needed to fit the next one in GPU memory.
- **Conversation duplication**: stores exist on both server (`conversations.json`) and client (IndexedDB); they mirror each other for durability.

## Common entry points for different types of tasks

- **Add/change an API endpoint** — `server.js` `handleAPI()`.
- **Change chat behavior/providers** — `server/providers.js`, `server/context-builder.js`, `server/conversation-service.js`.
- **Change task/intent routing or ActiveTask lifecycle** — `services/intent-resolver.js` (semantic intent), `services/task-router.js` (action routing + `decisionFromResolvedIntent`), `services/task-state.js`, `server.js` `handleChatStream` + `handleImageGenerationStream`.
- **Change Director Mode / multi-stage productions** — `services/director/*`, the director branch in `server.js` `handleChatStream`, the `opts.director` hooks in the image/video stream handlers, `public/js/director.js`, and the composer toggle `public/js/chat-director.js`.
- **Change UGC Studio / Product Library / UGC cards** — `services/ugc/studio.js` (stage machine, cards, continuity, natural editing, Director handoff input), `services/ugc/prompts.js` (LLM prompts + deterministic composers), `services/ugc/catalog.js` (content types/environments/platforms), `services/ugc/products.js` (Product Library), `services/ugc/state.js` (persistence), the UGC gate/handlers + `/api/ugc/*` endpoints in `server.js`, `public/js/ugc.js` (card + mode bar), and the `.ugc-*` styles. The Director handoff is `director.createUgcProduction` + the UGC `shotList`. Keep scripts facts-only and scene durations fitted to the requested total.
- **Change the Long Video Director / >15s routing** — `services/long-video/director.js` (router, Story Bible, beats, approval), `services/long-video/plan.js`, `services/long-video/prompts.js`, the long-video gate/handlers in `server.js` `handleChatStream`, and `public/js/long-video.js`. The ComfyUI graph lives only in `services/long-video/workflows/h3-longvideos.json`.
- **Change the Creative Playground / themes / character presets / Outfit Packs** — `services/playground/themes.js` (catalog), `services/playground/character.js` (identity generator + appearance/age/gender controls), `services/playground/outfit-packs.js` (wardrobe personalities + composition + context detection), `services/playground/concept.js` (assembly, locks, context interpretation, pack replacement), `services/playground/playground.js` (session + card + image/portrait requests), `services/character-presets.js`, the playground gate/handler + the face pre-render (`runPlaygroundFaceStage`) + `GET /api/playground/outfits` in `server.js`, `public/js/playground.js`, and `public/index.html` (`#chatSurprise`/`#chatPlaygroundPopup`). Generate must keep routing through `imageGenerator.buildImagePrompt` — never build the final Krea2 prompt inside the playground.
- **Change image generation / prompt / LoRA logic** — `services/image-generator.js`.
- **Change ComfyUI communication** — `services/comfyui.js`.
- **Change VRAM/unload orchestration** — `services/vram-manager.js`.
- **Change system telemetry** — `services/system-monitor.js`.
- **Change UI/UI logic** — `public/index.html`, `public/app.js`, `public/js/*`, `public/style.css`.
- **Change persisted settings schema** — `server/config-manager.js` (storage) + the relevant `sanitize*` in `services/image-generator.js` (or other service).
- **Add/remove a catalog model** — `server/models.js`.
