## Project overview

`not-so-jarvis` is a local AI assistant dashboard ("JARVIS") built with **plain Node.js** (no framework, zero npm dependencies) and **vanilla HTML/CSS/JS** (no bundler). It runs entirely on the user's machine with no cloud dependency. It provides:

- Chat with local AI providers (Ollama)
- System monitoring widgets (CPU, RAM, VRAM/GPU)
- A model library with hardware-compatibility detection
- AI image generation via a local ComfyUI instance using the **Qwen Image 2.1** text-to-image workflow (Krea2 is the optional alternate)

Version 0.1.0, MIT license. Entry point is `server.js`.

## Purpose of each important directory

- **`server/`** — Server-side application logic. These modules are required by `server.js` and do the actual work: chat, conversations, providers, config, model catalog.
- **`services/`** — Cross-cutting / independent services. `image-generator.js`, `comfyui.js`, and `vram-manager.js` together form the image generation pipeline. `director/` orchestrates Director Mode productions and `long-video/` orchestrates >15s videos. `system-monitor.js` provides telemetry, and `weather.js` provides server-side weather lookups for chat. `news.js` parses keyless RSS/Atom feeds for the NEWS widget and chat context. `generated-history.js` persists image metadata and `thumbnail.js` mints the gallery's cached low-res PNG thumbs in the background.
- **`public/`** — Everything served to the browser. `app.js` is the main entry; `public/js/*` are feature modules loaded as plain scripts (no modules/bundler).
- **`data/`** — Runtime persistence. JSON files are the source of truth for config/conversations/history; generated images land in `data/generated/`.

## Important services and integrations

- **Ollama** (`http://localhost:11434`) — chat provider via `server/providers.js`.
- **ComfyUI** (`http://127.0.0.1:8188`, overridable via `COMFYUI_URL`) — image generation via `services/comfyui.js`. Raw ComfyUI failures are classified (`classifyComfyError`) into stable codes (`comfyui_oom`/`comfyui_missing_model`/`comfyui_missing_node`/`comfyui_validation_error`) with actionable hints, and idempotent reads (`getObjectInfo`, `downloadImage`, `/history` polling) use bounded `withRetry` backoff for transient unreachable/5xx errors.
- **ComfyUI launcher** — `services/comfyui-launcher.js` starts a local ComfyUI server as a detached background process when it is offline. Resolution order: an explicit `COMFYUI_START_CMD` (env) or `comfyui.startCommand` (config) override, then ComfyUI Desktop (`installations.json` under the Electron userData dir, launching the standalone install's venv python + `main.py` headless), then a portable/venv layout (sibling `run_nvidia_gpu.bat`/`run_cpu.bat` or a resolved python). `comfyui.root` is cached in `data/config.json` when detected so a launch still works while ComfyUI is offline. `start()` is idempotent and single-flight, writes logs to `data/comfyui-start.log`, and polls `isAvailable()` until `COMFYUI_START_TIMEOUT_MS` (default 180s). Exposed by `POST /api/comfyui/start` (widget Start button) and the deterministic `isStartComfyRequest` chat gate in `handleChatStream` (so a "start comfyui" message never falls through to the chat model). `GET /api/comfyui/status` reports `canStart`/`startMethod` when offline.
- **Krea2 workflow** — assembled in `services/image-generator.js` (`buildKrea2T2IGraph`), using UNET/CLIP/VAE models configured through settings or env vars (`KREA2_*` in `.env.example`).
- **Qwen Image 2.1 workflow** — assembled in `services/image-generator.js` (`buildQwenImage21T2IGraph`), the default text-to-image pipeline selected by `imageGeneration.model` (`qwen_image_2_1`). Uses UNETLoader/CLIPLoader (`qwen_image`)/VAELoader with the `TextEncodeQwenImage21` core node and `EmptyLatentImage`; files come from `Comfy-Org/Qwen-Image-2.1` (env `QWEN_IMAGE_*` in `.env.example`). Downloaded by the Setup guide as required (it is the default); Krea2 is now the optional alternate.
- **Long Video Director** — `services/long-video/*` owns videos longer than H3's 15-second ceiling. The **duration router** (`director.isLongVideoRequest`, raw `parseRequestedSeconds`) sends >15s video requests to the Long Video Director and leaves <=15s on the existing H3 workflow untouched. The director builds a **Story Bible** (`plan.js` `data/long-video-state.json`) and a **beat plan** (one beat per shot, each <=15s, fewest beats possible; `prompts.segmentDuration` matches the documented splits 20→10+10, 25→13+12, 30→15+15, 40→13+14+13, 60→15×4), composes the paragraph-based prompt (paragraph 1 = scene, every later paragraph = one beat; **no `[Shot N]`**), and shows the storyboard once for approval. Approval submits **one** ComfyUI job to the installed `Smite79/MiniMax-H3-LongVideos` node (`H3LongVideos`), which performs the temporal chaining internally; `generator.js` never extracts a frame and never concatenates clips. `h3-longvideos-workflow.js` builds/validates the graph from the swappable config `workflows/h3-longvideos.json`, so the underlying ComfyUI workflow can change without touching the director. Contextual edits (`applyStoryboardUpdate`) rewrite the Story Bible and affected beats, never append to the old prompt. The plan/approval UI is `public/js/long-video.js` (`LongVideoUI`) with the persisted `[[longvideo:{...}]]` marker, `GET /api/longvideo/state`, and the `body.longVideoAction` button payload (`approve`/`modify_plan`/`retry`/`cancel`). Env: `H3_LONGVIDEO_MAX_SECONDS` / `H3_LONGVIDEO_STEPS` / `H3_LONGVIDEO_TIMEOUT_MS`.
- **Long Video motion continuity** — `services/long-video/motion.js` owns explicit motion/world-state continuity so beats don't behave like independent clips. Every beat carries an `ending_motion_state` (camera movement/direction/speed/momentum/orientation/framing/screenPosition, subject movement/direction/speed/pose/gaze/hands, moving objects, environmental movement) and an `ending_world_state` (clothing/appearance/location/props/objectStates/completedActions); every beat after the first carries `transition_from_previous` (`initial_continuation` → `transition` → `new_action` → `resulting_motion_state`). `motion.reconcileMotionChain()` runs after every plan/build/update: it normalizes states, carries world state forward (completed actions and object states are never re-executed), and **fills/repairs** each transition from the previous beat's actual ending state — continue → decelerate/reverse/settle → new motion (pan→push-in passes through "the pan settles, then a gentle push in begins"; reversals pass through "carries its pan briefly, gradually slows, then smoothly reverses"). Planner-provided transitions are preserved; gaps are filled deterministically. `transition_mode` is `continuous_transition` (default) or `abrupt_transition`, auto-detected from cut/jump/sudden wording. `composeLongVideoPrompt` writes these as plain cinematic prose — schema field names are never sent to H3. Because the LongVideos node renders all beats in ONE job, the ending states are planned (not observed from generated frames); the node still owns the actual frame-to-frame conditioning.
- **UGC Studio** — `services/ugc/*` is a chat-first workflow layer (not a separate dashboard). A UGC request ("create a UGC video for my product", "make a TikTok ad", "write me a UGC script") is caught by a deterministic gate in `server.js` `handleChatStream` *before* the Long Video/Director gates and the task router, so a brief never becomes a normal image/video generation and a >15s UGC request is not captured by the duration router. `studio.detectUgcIntent` (noun + action) drives it; the project stage is tracked by the application, not the LLM. **The default creation flow is a single step, set up in the popup.** The UGC popup (`public/index.html` `#ugcStudioOverlay`, populated from `GET /api/ugc/options`) is the setup surface: product (a library pick or a new facts-only record), creator (a saved character, a rolled creator with optional appearance/age/gender controls, or product-only), content type, outfit pack or custom outfit, environment or custom environment, duration, platform and the brief fields. Its **Create UGC video** button sends `body.ugcAction = { type: 'create_project', setup }`; `handleUGCStart` applies the setup via `studio.autoSetup` (explicit selections win, anything unset falls back to a deterministic auto resolution: an exact library match or the brief's product name, a mentioned/rolled creator, the character wardrobe pack or `casual-everyday`, the brief's environment/content type or a neutral default), then `handleUGCAutoRun` runs script → scenes → `handleUGCGenerateReferences` (silent, no standalone card) → `approveReferences` → `handleUGCDirectorHandoff` in one stream, so no brief/script/scene/reference approval card is shown on the happy path. A text-only UGC request in chat still works: it starts a project with auto-resolved setup. The `[[ugc:{...}]]` cards and the `brief` → `product_selection` → `creator_selection` → `creative_direction` → `script_review` → `scene_review` → `reference_generation` → `reference_approval` → `video_generation` → `completed` stage machine are retained for recovery (a failed frame batch surfaces the reference-approval card so failed frames can be retried, and the full `/api/ugc/*` action space still works). Actions arrive as `body.ugcAction` and typed follow-ups are classified by `studio.classifyMessage` (conservative — unrelated requests fall through to the normal router). Each card is carried by a persisted `[[ugc:{...}]]` marker (stripped from model context in `context-builder.js`). Projects persist to `data/ugc-state.json` (`GET /api/ugc/state`); exiting keeps a draft (`status: draft`) that resume reactivates. Product Library (`data/ugc-products.json`, `GET/POST /api/ugc/products`, `DELETE /api/ugc/products/:id`) stores only user-supplied facts — never invented claims. Script/scene generation use the chat LLM with facts-only system prompts and deterministic fallbacks (`prompts.js`); scene durations are always fitted to the requested total (`studio.fitDurations`). Dialogue is always fitted to a natural speaking pace: `prompts.SPEAKING_WORDS_PER_SECOND` (≈2.3) + `prompts.dialogueWordBudget`/`fitDialogueToBudget` cap each scene's line to its duration (a 5s cut carries ~11 words), `prompts.enforceDialogueBudgets` runs in `studio.save()` so no path can persist an over-long line, and the script/scene/regenerate prompts carry an explicit word budget (an over-long line is delivered too fast and sounds robotic). Continuity (`studio.reconcileContinuity`) pins creator/outfit/environment across scenes. Reference frames reuse the image pipeline (`studio.buildReferenceRequest` → `imageGenerator.buildImagePrompt` → `imageGenerator.generateImage`) and are recorded in the gallery. The approved project hands off to the existing Director Mode via `director.createUgcProduction`: the UGC scene plan becomes the Director brief's `shotList` (structured, never a text blob) and **every approved scene reference frame** travels with the production (`production.references`); the Director's video stage conditions H3 on all of them via the core `MiniMaxH3ReferenceToVideo` node (reference-to-video, addressed as `<Picture 1..N>`, `videoMode: 'ref2va'`), instead of animating only a single opening frame; each scene's `dialogue` is carried into that `shotList` as an on-screen `(S1)`/`<d>[English] …</d>` line (never a raw `script:` blob in `details`, which H3 read as voiceover and left the mouth closed), and the deterministic scene fallback distributes the approved script across scenes (`prompts.distributeDialogue`) so a failed scene LLM still speaks on camera; the spoken language (default English, or a named language in the request via `prompts.dialogueLanguageFor`) is written into the `<d>[Language]` tag and the approved line is re-asserted deterministically by `videoGenerator.ensureShotDialogue` after the H3 director LLM, so a dropped dialogue block can never make H3 invent speech in its own language; `handleUGCDirectorHandoff` then runs the existing `runDirectorVideoStage`. The UI is `public/js/ugc.js` (`UGCUI`, loaded before `chat.js`) with the `.ugc-bar` "UGC Studio · Active" indicator and `.ugc-*` cards. Tests: `test/ugc.test.js`.
- **UGC Studio integrity rules** — `services/ugc/studio.js` owns a canonical brief schema (`BRIEF_FIELDS`: objective, productName, brand, productCategory, contentType, platform, duration, aspectRatio, targetAudience, tone, keyMessage, callToAction, environment, dialogueLanguage, creatorDescription, additionalInstructions) that must survive extraction, `mergeBrief`, normalization, save/reload and regeneration. Every server action is validated against the live stage by `studio.validateAction` (never trust the UI), stale cards are rejected by `studio.isStaleAction` (project `version`), and overlapping actions are serialized per conversation in `server.js`. References are fingerprinted by `studio.currentPlanHash` (visual fields only — scene id/order/duration/action/camera/productVisibility/environment/outfit, plus creator/outfit/environment/product/aspect/duration): any visual edit calls `studio.invalidateReferences` (clears `approvedReferences`, marks frames stale), `studio.approveReferences` requires exactly one current frame per scene (missing/stale/failed/duplicate reject), `studio.referencesComplete`/`pendingReferenceSceneIds` drive the UI, and `studio.recordReferenceFailure` preserves partial successes for retry-failed-only. Duration is bounded by `prompts.DURATION_LIMITS` (1–60s planned, 15s render ceiling): `prompts.validateDuration` validates edits, `studio.resizeScenesForDuration` recomputes scene count/durations, and a >15s brief is **never silently clamped** — the handoff explains the cap and requires an explicit `confirm_duration` ("continue at 15 seconds"). Creator-free (product-only) mode is explicit (`studio.skipCreator` → `creatorMode: 'none'`), and script/scene/reference/Director prompts never invent a person. LLM output is validated facts-only (`prompts.validateScript`/`validateScenes`: unsupported price/guarantee/certification/medical/result/superlative/personal-experience claims stripped and flagged `needsConfirmation`, usage verbs checked against `usageInstructions`, dialogue trimmed to budget, duplicate scene IDs repaired). Product reference images travel on a separate `product_references` channel (never merged with scene frames). A saved product can be removed from the library via the product card's delete action (`studio.deleteProduct`, validated like every other action; the project keeps its own snapshot, and `DELETE /api/ugc/products/:id` remains for direct API use). Lifecycle: `studio.syncDirectorOutcome` (matched by the existing `directorProductionId`) marks the linked project `completed` on Director success (so it stops intercepting chat) or returns it to `reference_approval` with `lastError` on failure/cancel. **Reference frames are internal media:** every UGC frame render is recorded `hidden: true` in `generated-history` (out of the gallery, the ACTIVITY feed and the `@` picker) but stays on disk so the card previews and the Director's `ref2va` handoff can use it. Because hidden frames are never linked from chat messages, `removeConversationImages` cannot find them; `server.js` `removeUGCMedia` collects them with `studio.referenceFilenames(project)` and calls `generatedHistory.removeByFilename` for each, then drops the project record — so deleting the conversation also deletes its UGC reference frames. Tests: `test/ugc.test.js`.
- **Director Mode** — `services/director/*` coordinates video production. Video requests run through the normal H3 pipeline by default — there is no Direct-video-vs-Director-mode question. Director mode starts only when the user asks for it explicitly, either by typed phrasing (`director mode`, `as a director`, `wantsDirectorMode`) or the composer **Director Mode toggle** (`public/js/chat-director.js`, `#chatDirector`), which sends `body.forceDirector`; `director.shouldForceDirector(message, decision)` then routes a fresh video turn (`new_task`/`switch_task`) straight to the Director, while explicit "just generate the video" (`wantsDirectMode`) still wins and `continue_task` tweaks of an active video task are untouched. The toggle also **supersedes the long-video duration router**: `director.shouldForceDirectorOverLongVideo(message, { forceDirector, longVideoBusy })` lets a `>15s` request with the toggle on bypass the Long Video gate and start the Director instead (and any parked long-video storyboard is dropped so its approval can't capture the production), while explicit `wantsDirectMode` and an actively rendering long video still win. Because the Director's video stage is H3, a `>15s` toggle request is clamped to the 15s ceiling by `parseRequestedVideoDuration`. Choosing Director builds the canonical brief and runs opening image → approval checkpoint → H3 I2VA video. `buildVideoStageRequest` conditions the H3 video on the single approved opening frame (`i2va`), or, when the production carries `references` (the UGC handoff), on every approved scene frame at once (`ref2va`, addressed as `<Picture 1..N>` through the core `MiniMaxH3ReferenceToVideo` node). The canonical creative brief (`production-plan.js`, persisted to `data/director-state.json` per conversation) is the source of truth: a direction change updates the brief via `director-prompts.js` and rebuilds the image prompt, never appends to the old one. The brief has a free-form `details` catch-all (props, wardrobe, dialogue, named styles) so specifics survive the structured fields, and while `briefModified` is false the compose functions also carry the user's original wording as authoritative context for the image/H3 prompts. **Director productions are cut like a film, not one continuous take:** the brief carries an ordered `shotList` (planned by the brief LLM, with `director-prompts.planShots` as the deterministic fallback — roughly one cut per three seconds, capped at five, unless the user explicitly asks for a single take), `composeVideoDirection` translates it into a numbered shot plan, and `buildVideoStageRequest` passes `shot_plan`/`multi_shot` into `videoGenerator.buildH3VideoPrompt`. When a shot plan is present the H3 director switches to the `H3_MULTISHOT_ADDENDUM` (official guide cut syntax: `[Shot N] At 00:0S.SSS, the camera cuts to …`, strictly increasing, no timestamp on `[Shot 1]`), a rewrite with fewer than two `[Shot N]` markers is rejected and retried, and the deterministic `buildMultiShotFallbackPrompt` emits the plan even if every LLM step fails. The normal direct-video pipeline carries no shot plan and stays single-shot unless the user explicitly requests multiple shots. The Director decides WHAT runs; `image-generator.js`/`video-generator.js` decide HOW. **Spoken dialogue is on-screen speech, not narration:** the H3 director system prompt (`H3_DIRECTOR_SYSTEM_PROMPT`, also in the multishot addendum) teaches the official speaker/dialogue syntax — stable `(S1)`/`(S1,S2)` speaker IDs, the speaker named and on screen with their mouth described as visibly lip-synced while they speak, the exact words preserved verbatim inside `<d>[Language] …</d>` (never translated/rewritten/invented), off-screen voiceover only when the user explicitly asks for narration (then "lips remain completely closed"), and dialogue kept out of `overall_soundscape`. Director briefs carry spoken lines in the brief's `shotList` in that form so `composeVideoDirection`/`buildH3VideoPrompt` preserve them. The server executes stages through the existing `handleImageGenerationStream`/`handleVideoGenerationStream` by passing `opts.director` (those handlers emit a `director` SSE card instead of the normal `image`/`video` event, mark the production stage ready/failed, and stop at approval); the direct-video pipeline runs the normal H3 path. Actions arrive as `body.directorAction` on `/api/chat/stream` (button clicks) or as typed decisions (`approval-manager.js` `classifyMessage`); `GET /api/director/state?conversationId=` restores card interactivity after a reload. The approval card also offers **Upscale Frame** (`approval-manager.js` `UPSCALE_IMAGE`, typed "upscale the frame" included): `runDirectorUpscaleStage` runs the shared image upscaler (`imageGenerator.upscaleImage`, SeedVR2/Ultimate SD — the single UPSCALE settings) on the opening frame, then `director.markImageUpscaled` points `production.image` at the `_up_` file (keeping `upscaled`/`upscaledFrom`) while the production stays at the approval checkpoint, so `buildVideoStageRequest` animates the higher-resolution frame. A failed upscale is non-terminal (`markUpscaleFailed`): the original frame and the approval card stay usable.
- **VRAM manager** — `services/vram-manager.js` enforces "one side resident, always": Ollama and ComfyUI are never loaded at the same time, and there are **no memory-pressure thresholds** (a pre-action check can see a healthy machine while both footprints are already stacked — e.g. right after a generation evicted the chat model but ComfyUI still holds its weights). Before any chat work `freeVRAMBeforeChat` unloads ComfyUI models; `comfyui.queuePrompt` sets a residency flag (`comfyui.hasResidentModels`/`forgetResidentModels`) so it skips the round-trip when the app queued nothing. The free now runs at the **start of the chat turn, before `taskRouter.routeMessage`** (`server.js` `handleChatStream`) because routing and image/video prompt building both consult the Ollama model — waiting until the chat-reply branch would let both load during routing. Before any image/video generation `freeVRAMBeforeImage` unloads **every** model Ollama has loaded (discovered from `/api/ps` via `providerManager.getOllamaStatus`, with `rememberChatModel` as a fallback), so a model loaded outside the app or before a restart is still evicted. **No Ollama call may run after a ComfyUI job until ComfyUI is freed** — the post-generation confirmation (`taskRouter.buildSuccessReply`) is therefore called with `deterministic: true` in the image/video/edit handlers (template sentence, no LLM), because ComfyUI keeps its weights resident until the next turn's `freeVRAMBeforeChat`; invoking the summary LLM there reloads the GB-scale chat model on top of them and froze the machine. Eviction is **verified**: `keep_alive 0` only schedules the unload, so `waitForChatRelease` polls `/api/ps` until each model is actually gone (bounded by `JARVIS_MODEL_RELEASE_TIMEOUT_MS`, `JARVIS_MODEL_RELEASE_POLL_MS`) then holds `JARVIS_MODEL_RELEASE_SETTLE_MS` so the OS reclaims the RAM before ComfyUI loads — without it a still-resident llama-server stacked under the video model and froze the machine. The ComfyUI side (`freeVRAMBeforeChat`/`freeComfyModels`) holds the same settle after `/free`. Every wait is per-call overridable (`opts.policy`-free `{ timeoutMs, pollMs, settleMs }`) so tests stay fast. The tradeoff is deliberate: a generation unloads and reloads ComfyUI per image/video turn, because prompt building needs Ollama first. `reconcileOnStartup()` (called from `server.listen`) frees ComfyUI models left over from a previous process. Director stages go through `prepareDirectorLlm` before their interleaved Ollama planning calls and `freeComfyModels` at the end of a stage.
- **Open-Meteo weather** — `services/weather.js` fetches current conditions (no API key) for the browser-reported location. The dashboard widget POSTs its geolocation to `/api/weather/location`; the server persists it in `data/config.json` (`weather` key) and injects a gated snapshot into chat context. `GET /api/weather` returns the cached current conditions.
- **RSS news** — `services/news.js` fetches keyless RSS/Atom feeds (curated defaults: BBC World, NPR, Hacker News), parses them with a regex reader (`parseFeed`), and caches the merged items for 10 minutes. The NEWS widget polls `GET /api/news` with a `category` scope (`all`/`global`/`local`) and a segmented ALL/GLOBAL/LOCAL control; `POST /api/news/settings` persists the custom feed list and the `localArea` used by the `local` scope in `data/config.json` (`news` key, sanitized by `config-manager`), resetting feeds to defaults when sent empty. `GET /api/news?topic=…` uses keyless Google News RSS search, and the `local` scope searches the saved area (area + extracted topic). Headlines are treated as untrusted data and always link out to the source.

- **Character Identity System (Character Playground 2.0)** — `services/character-identity.js` turns an approved character into a reusable identity package stored on the character record (`character-presets.js` `getIdentityPackage`/`setIdentityPackage`/`clearIdentitySheet`). **The cardinal rule: one character = one approved base image + ONE consolidated Character Identity Sheet image.** The sheet is a single composite image holding multiple reference panels (full-body front / three-quarter / side profile / face close-up, plus conditional accessory / distinctive-feature / hair detail panels only when the identity carries that detail); the identity package never stores a per-angle reference array. A character is **candidate → approved → generating_identity → ready/failed** at the model level. **Saving a concept as a character creates the identity sheet directly** (`Save as Character` → `save_character`): `handlePlaygroundAction` creates the preset, locks the card preview as the approved base image (`baseImageFromSession` prefers `session.characterImage`; only when none exists is a fresh 1024×1024 base rendered), then immediately runs `runIdentitySheetStream` — there is no separate candidate-approval step. `POST /api/characters/:id/identity/approve` and the `identity_approve`/`identity_regenerate` actions remain available as a recovery path but are not part of the normal flow. Generation reuses the **Qwen Image 2.1 edit pipeline** (`imageGenerator.editImage`, never a new engine) with the approved base image as `image_1` and a single neutral studio-reference instruction (`buildIdentitySheetPrompt`), producing exactly one file. A generation runs over SSE (`generating`/`identityProgress`, then an `identity` card); a failed first run marks the package failed, while a failed **regeneration** keeps the previous valid sheet and the approved base (`markSheetFailed`). `buildCard` returns a paths-free card with `approvedBaseImage`, the single `identitySheet` (`{ url, filename, version, status }`), `identityMetadata` and `identityPreservationInstructions` for the viewer (`public/js/character-identity.js` `CharacterIdentityUI`, modal `#identityOverlay`; "Use Character" inserts an `@Name` mention into the composer). `deriveMetadata` maps the structured identity onto `face`/`hair`/`skin`/`body` + `distinctiveFeatures`/`signatureAccessories`, and the `skin` block is now structured (`tone`, `baseTone`, `undertone`, `complexion`, `identityCritical`, `consistencyInstruction`) so skin is a persistent identity attribute, never a flat RGB value (`completeSkinMetadata`/`skinDescriptor`; legacy metadata is filled deterministically on load and nothing is invented when the identity carries no skin information). **Skin-tone continuity is part of the identity layer:** `buildSceneEditInstruction` adds a `CHARACTER SKIN-TONE CONTINUITY` section (one underlying complexion across face/ears/neck/shoulders/chest/arms/hands/legs; lighting changes how it is perceived but never the complexion itself; the neck must visually connect face and body; natural highlights/shadows/subsurface scattering allowed, no artificial colour boundary) and `buildIdentityConstraints` carries the same rule; `buildIdentitySheetPrompt` establishes the complexion once on the sheet. The identity-vs-scene layer (`buildIdentityConstraints`, `buildSceneEditInstruction` — explicit IDENTITY / SKIN-TONE CONTINUITY / OUTPUT / SCENE / DO NOT sections) keeps permanent identity (including complexion) separate from changeable outfit/environment/pose/lighting. **Generation never uses the multi-panel sheet as its primary/preferred image:** `selectIdentityReference` returns the single approved base portrait as `primary`, with the sheet only as a supplementary `sheet` reference (and `hasSheet`). The Qwen editor reproduces the layout of its primary source, so feeding it the sheet renders a fresh collage of panels. **Image generation** conditions a named/bound approved character through reference-guided edit (`resolveIdentityConditioning` → `handleImageGenerationStream` `opts.identity`) on the base portrait plus the sheet as a supplementary reference (`includeSheets: true`); **video generation** passes only the single base portrait per character (`MiniMaxH3ReferenceToVideo`, `ref2va`, `includeSheets: false` — a multi-panel reference would bleed into the clip); **Director Mode** carries `production.identityReferences` (base portraits only) so every shot inherits the same person; **UGC Studio** stores the creator's `identityReferences` (base portrait)/`identityBaseImage`/`identitySheetImage`/`identityMetadata` (`selectCreator`), conditions its reference frames on the base portrait with the sheet as a supplemental reference, and passes base-only references through `directorProductionInput` → `createUgcProduction`. APIs: `GET /api/characters/:id/identity`, `DELETE /api/characters/:id/identity` (sheet only), `POST /api/characters/:id/identity/approve`, `POST /api/characters/:id/identity/sheet`. Identity is reference-guided consistency, never guaranteed identical facial reproduction. Tests: `test/character-identity.test.js`.

- **Character mentions (@Character) + shared character context** - `services/character-context.js` is the single place that turns a user message into structured character context, so image/video/Director/UGC never parse `@Maya` themselves. The chat composer's `@` picker (`public/js/chat.js`; options from `GET /api/characters/options` via `listCharacterOptions`) shows saved characters with their identity status (`ready`/`generating`/`failed`/`basic`/`none`) and primary image, then the conversation's images, then **Create New Character** (opens the existing Creative Playground — `PlaygroundUI.open`; no second creation workflow). Selecting a character inserts an `@Name` token and a chip and sends a structured `body.characters: [id]`; `@Name` is stripped from the working message (`parsedCharacters.prompt`) but kept in the persisted user message, and the prompt builder receives scene direction, not the token. `parseMentions` matches only known character names (longest first, text order preserved) and never an email local part; `matchNames` resolves bare names ("bring Maya back"). The per-conversation active character store (`data/character-context.json`, env `CHARACTER_CONTEXT_PATH`; `get/set/clearActiveCharacter`) is scoped to the generation flow: an explicit mention/picker selection **switches** it, explicit removal wording ("without her", "no character", "just the scene") **clears** it, a continuation ("make her …", "she") **inherits** it, and a fresh characterless generation does not. `buildConditioning` contributes one primary identity image per character (`character-identity.selectIdentityReference` — the approved base portrait; the consolidated identity sheet when ready rides along as a supplementary still-image reference via `sheetFilenames`, dropped for video with `includeSheets: false`) and separates identity from scene (`buildSceneInstruction` — a single character keeps the existing reference-guided IDENTITY/SKIN-TONE CONTINUITY/SCENE/DO NOT instruction unchanged; **2+ referenced characters switch to a dedicated multi-character identity mode**, `buildMultiCharacterInstruction`, ordered CHARACTER IDENTITY → CHARACTER ATTRIBUTE ISOLATION → CHARACTER SEPARATION → REFERENCE IMAGE ROLES → SCENE → CHARACTER-SPECIFIC ACTIONS / POSITIONS → SKIN-TONE CONTINUITY ACROSS CHARACTERS → OUTPUT CONSTRAINT. Each character gets a numbered `CHARACTER N — NAME` block that maps `Reference image N` to that one character and preserves that character's named facial identity/hair/skin/body (never an ambiguous "their"); attribute isolation enumerates face shape, eyes, nose, mouth, facial structure, freckles/marks, hair colour, hairstyle, skin tone, skin undertone, body proportions, body build and complexion as non-transferable; separation names every character and forbids merging/swapping/blending/cross-assigning; reference roles state `Reference image N = Name only` and that references are identity sources, never composition/pose/background/lighting/framing/panel sources; the actions section (`buildCharacterActionSection`) rewrites the user's own wording into name-owned `[name] + action + position` assignments, preserves explicit names, and resolves singular/plural pronouns to a named antecedent only when one appears in the same sentence (ambiguous scenes are preserved, not guessed at); skin continuity is per-character (`Name retains Name's natural complexion`) while scene lighting is applied equally; output is exactly ONE new standalone scene image with no sheets/turnarounds/collages/panels. The per-character section also rides on the conditioning object as `conditioning.multiCharacter` (`{ count, names, section }`). `server.js` threads the raw user message (`message`, still carrying `@Name`) into `resolveIdentityConditioning(..., { rawPrompt })` so action ownership is derived from the user's own phrasing). `server.js` resolves once after routing (`resolveRequestCharacters`) and threads the result: image generation runs `editImage` (multi-character: the first character's identity image is the source, each later character contributes exactly one positional reference, and user `@image` refs follow); video runs ref2va with the single identity images **unless a user-provided I2VA frame exists** (that frame is never replaced); Director carries the identity images across every shot; UGC auto-selects a mentioned creator via `studio.selectCreator`. **Character + `@image` references combine**: when a `@Character` and one or more `@image` refs are present together, the router's `@`-reference gate returns `image_edit`, but the server's `image_edit` branch detects the active character and instead runs `handleImageGenerationStream` with identity conditioning — the character's identity image stays the edit source (`image 1`) and the user's `@image` refs ride along as positional scene references via `character-context.combineReferenceFilenames` (`addUserReferencesToInstruction` names them by `image N`), so the character is never dropped. Characterless `@image` turns keep the plain edit. Identity media is protected from conversation deletes: `removeConversationImages` (which drops unlinked generated media when a conversation is deleted) skips every filename owned by a character identity package (`characterContext.characterMediaFilenames()` — the approved base image + the single identity sheet), because those files are hidden and never linked from chat messages yet the character record still points at them. This is what keeps a saved character alive after its conversation is deleted. Tests: `test/character-context.test.js`.

- **Shared Scene / Location Library** — `services/scene-library.js` is the **ONE canonical source** of environment/scene data. It promotes the original UGC environment catalog (the first nine built-in scenes retain their exact UGC ids, names and descriptions) into a persisted, user-manageable library (`data/scenes.json`, env `SCENES_PATH`), and **automatically migrates** any custom environment already stored on a UGC project (id/name/description/`referenceImages` retained, idempotent). A Scene carries `{ id, name/label, category, description, environment {architecture,furniture,props,materials,colors}, lighting {description,timeOfDay}, atmosphere, cameraContext, referenceImages/referenceImage, suggestedActivities, tags, source, createdAt, updatedAt }`. There is **one UI concept with two labels**: UGC Studio shows **Environment** (`#ugcEnvironment`, populated from `ugcStudio.listEnvironments()` → the library, plus the legacy `custom` free-text entry) and Creator Studio shows **Scene** (`#creatorScene` select + a Custom text field, options from `creatorCatalog.scenes`). UGC stores a Scene snapshot on `project.environment` (old `{id,label,description}` records are enriched by `snapshot()` and still resolve). **`buildSceneContext(scene, options)` is the single shared builder** that turns a Scene into consistent natural-language context (summary + structured detail + `prompt`, plus `referenceImages`, `tags`, and the outfit-resolver classification); it never invents detail. UGC's `prompts.referenceConcept`/`directorBrief` and Creator Studio's shot environment use it. **Activity→Scene recommendations** come from `sceneLibrary.recommendForActivity(activityId)` / `selectSceneForActivity` (reusing the Activity Library's `environments.preferred/compatible` tokens against each Scene's id/tags/suggestedActivities) — recommendations only, an explicit Scene always wins. The Creative Playground resolves Scene as an **independent dimension after Activity** (`concept.resolveConceptScene`): an explicit library id wins, `auto` picks from the Activity's recommendations, `random` picks any, and the theme's own environment wording remains the default when no shared Scene is requested (a locked environment or a user prompt owns the scene). API: `GET /api/scenes`, `GET /api/scenes/options`, `GET /api/scenes/recommend?activity=`, `POST /api/scenes` (create/update), `POST /api/scenes/:id/duplicate`, `DELETE /api/scenes/:id`. Creator Studio passes a selected Scene's reference image as an optional lower-priority semantic H3 reference (environment only, never identity). Scene stays separate from Activity, Outfit, Character and Expression. Tests: `test/scene-library.test.js`.

- **Creative Defaults (auto clothing + image style)** — `services/creative-defaults.js` fills the creative detail a user leaves unspecified: **user instructions always win, and the user is never asked**. It is invoked by `character-context.buildConditioning`/`buildSceneInstruction` (single character appends a `CLOTHING` + `IMAGE STYLE` section to the existing instruction; multi-character folds each character's clothing into its own `CHARACTER N — NAME` block and adds one shared `IMAGE STYLE` section). It never builds the final prompt itself — it is a structured contribution to the instruction. **Clothing** reuses the existing Outfit Pack / theme wardrobe system, never a second pool: an assigned pack (`character.outfitPack`) or a pack detected from the scene drives `outfitPacks.composeFromPack` (gender-aware); with no pack the scene picks a wardrobe personality from the same 12-pack catalog (`defaultPackForScene` — gym→`gym-activewear`, evening→`casual-night-out`, bedroom→`lounge-home`, warm→`vacation-summer`, outdoor→`casual-streetwear`, else `casual-everyday`); a **"getting ready" occasion cue** (`occasionPack`) outranks the room's wardrobe hint so "getting ready for a date in her bedroom" is a night-out/date look, not loungewear. Composition is deterministic per character+seed (`mulberry32`), so a multi-character scene gives each person an **independent** outfit that never repeats another character's. **Every composition is reconciled with the environment** through the central resolver (`services/playground/outfit-context.js` `resolveOutfitForEnvironment`): the environment/scene is classified into a context (bedroom/cafe/gym/beach/office/date night/…) and heavy outerwear is removed indoors, footwear is adapted to the setting, and accessories are minimized in private/exercise contexts — while an explicit user garment is never touched. `outfit-packs.composeFromPack` post-filters a gender-inappropriate result (a dress/camisole/leggings/skirt on a male character with an untagged pack) and retries with a neutral separates look, falling back to `casual-everyday`. A male character is composed with `archetypes: ['separates','layered']`. **Style** is a coherent package (`STYLE_PACKAGES`) chosen by scene type — casual social/everyday scenes default to `smartphone` (selfie wording → `selfie`, nightlife → `night`) while product/studio/cinematic/editorial/film/illustration/painting/anime/documentary requests keep their own treatment; `detectExplicitStyle`/`specifiesStyle` suppress the default whenever the user names a style. **Explicit detection**: `specifiesClothing` (garment vocabulary) and `specifiesStyle` (style presets + style words) suppress the matching auto slot entirely; a **partial garment instruction** (e.g. "wearing a white crop top") fills only the *missing* slots via `outfit-context.detectClothingSlots`/`stripSlots` (a named top/bottom also excludes one-piece looks so the fill cannot contradict the user), while a complete outfit (one-piece, suit, or top + bottom) still suppresses auto-fill, and multi-character scenes stay conservative (any explicit clothing suppresses). **Continuity**: a follow-up/edit preserves the previously resolved clothing/style (`continuity` + `previousClothing`/`previousStyle`, persisted on the task as `parameters.clothing`/`imageStyle` by `server.js` `persistedClothing`/`persistedImageStyle`) unless the user asks to change them; a new standalone scene generates fresh defaults. Priority is IDENTITY → user attributes → user scene → user clothing → user style → automatic clothing → automatic style, so identity always wins. Video and Director pass `defaults: false` (they only consume identity references). `JARVIS_PROMPT_DEBUG=1` prints the resolved instruction with whether clothing/style were explicit or automatic. Tests: `test/creative-defaults.test.js`.

Character generation conditioning rule: the consolidated multi-panel identity sheet is display/archive-only and must never be sent to image or video models, including as a secondary reference. Use the approved single portrait as the edit source and structured identity metadata as the additional identity signal. Creative Playground random characters must use their pre-rendered portrait through the same Qwen reference-guided edit path as saved `@Character` requests; if that portrait cannot be established, do not silently fall back to text-only character generation. This supersedes older descriptions above that call the sheet a supplementary still-image reference.

- Both chat paths (`handleChat`, `handleChatStream`) call `buildEnvironmentContext(message)` before `contextBuilder.buildContext`, appending a system message with live telemetry (`contextBuilder.buildSystemStatsContext`, gated on `SYSTEM_QUERY_RE`), weather (`weather.buildWeatherContext`, gated on `WEATHER_QUERY_RE`), and news (`news.buildNewsContext`, gated on `NEWS_QUERY_RE`). ## Important architectural patterns

- **No framework on either side.** Node `http` server + vanilla JS frontend. `server.js` has all routing defined as a sequence of path+method checks inside `handleAPI()`.
- **Service modules exported as plain objects** with named functions; no classes (except `system-monitor.js` which uses a class).
- **Persistence is simple JSON files** in `data/`, rewritten in full on mutation. No ORM/schema library.
- **Frontend mirrors backend persistence**: conversations are also stored client-side in IndexedDB (`public/js/db.js`) for UI durability.
- **Image generation idempotency/locking**: only one image generation at a time, enforced by `withGenerationLock` in `image-generator.js`.
- **Turn serialization (LAN multi-client)**: `server.js` binds to `HOST` (default `0.0.0.0`) so devices on the same WiFi can reach the dashboard (the LAN URL is printed at startup; `HOST=127.0.0.1` makes it local-only). Because every turn swaps the Ollama/ComfyUI model sets and the shared `generation-queue` only serializes ComfyUI jobs, whole turns are serialized by `services/turn-queue.js`: `acquireTurn(res, opts)` wraps `handleChat`, `handleChatStream`, `POST /api/upscale` and `POST /api/video/upscale`, so a second client waits (FIFO) and is told over SSE (`{ queued: { position, turnId } }`) instead of racing the first. The slot is released on the response `finish`/`close`; a waiting turn is cancellable via `POST /api/queue/cancel { turnId }`. Control endpoints (`/api/queue/cancel`, `/api/comfyui/cancel|free`, `/api/queue`) deliberately bypass the gate. The inner generation-queue is unchanged, so there is no lock nesting/deadlock.
- **Long Video Director / duration router** — `services/long-video/*` handles videos over H3's 15s ceiling. In `handleChatStream`, *after* the deterministic "start ComfyUI" gate and *before* the Director Mode gate, `longVideoDirector.isLongVideoRequest` routes >15s requests to `handleLongVideoStart` (plan + storyboard card) and `handleLongVideoAction` (approve/modify/retry/cancel). It is independent of Director Mode: <=15s requests never reach it, so the existing H3 workflow is unchanged. `motion.reconcileMotionChain()` keeps every beat's camera/subject motion and world state continuous across the chain (see "Long Video motion continuity"). The installed `H3LongVideos` node does the actual chaining — JARVIS builds one prompt and submits one job; it must never add FFmpeg last-frame extraction or per-clip concatenation.
- **UGC Studio gate** — runs in `handleChatStream` immediately after the deterministic "start ComfyUI" gate and *before* the Long Video/Director gates, the Playground gate, and the router. An explicit `body.ugcAction` executes a card action; a typed follow-up to an active project is classified by `studio.classifyMessage`; a new `detectUgcIntent` request starts a project and runs it to video in one step via `handleUGCAutoRun`. Unrelated turns fall through, so normal chat/image/video generation still works (and stays untouched when UGC is inactive). Exiting sets the project to `draft`; `discard` removes it, and `new_project` (the completed bar's "New project") clears the finished project record so a fresh one can start without deleting the generated video. UGC frames are built as creative direction and handed to `imageGenerator.buildImagePrompt` — the studio never builds the final Krea2 prompt.
- **Intent Resolver layer (primary decision-maker)** — `services/intent-resolver.js` sits between the user message and the action router: `User Message → Context Builder → Intent Resolver → Structured Intent → Action Router (task-router) → Action`. `resolveIntent()` combines the current message, a compact conversation context (`buildIntentContext`: last user request, last assistant action, last generated image/video, active prompt/generation, selected video mode), explicit wording, and regex signals (`collectSignals`) into a structured intent `{ intent, confidence, mode, referencesPreviousContext, referencedGenerationId, extractedRequest, subject, creative_mode, explicit_constraints }`. Intents: `chat`, `image_generation`, `video_generation`, `prompt_writing`, `prompt_ideation`, `modify_previous_generation` (+ `image_edit`/`image_upscale`/`video_upscale`). The **action is decided first; media words ("image", "video", "prompt", "portrait", "cinematic") are only subject/context** — "write me a prompt for an image" is `prompt_writing`, not `image_generation`. The resolver NEVER executes a tool; `task-router.decisionFromResolvedIntent()` maps the structured intent to the executable decision. `mode` (video) is inferred without asking: `director` only for explicit Director wording, `direct` for every other video request. Priority hierarchy: **A** explicit user action ("director mode", "write a prompt …") → **B** semantic LLM (final authority when ambiguous, temperature 0, malformed JSON retried once, **`think: false`** — every chat-path classifier call (resolver, `task-router.askRouter`/`buildSuccessReply`, `imageGenerator.detectIntent`, `videoGenerator.detectVideoIntent`) pins reasoning off so a hidden thinking pass never delays the turn or piles GPU load onto the reply) → **C** regex/keyword signals (evidence only) → **D** chat fallback. Context inheritance is conservative: `referencesPreviousContext` requires a clear reference ("this"/"that"/"her"/"the image"/"make it …"/"change …"), so an unrelated new request never inherits the previous generation. Set `JARVIS_INTENT_DEBUG=1` (or pass `{ debug: true }`) to print the resolver decision, the regex evidence, and the final action.
- **Canonical turn plan** — after the UGC / Long Video / Director / Playground gates, `task-router.planTurn()` wraps the existing decision in a versioned plan containing conversation/task context, references, selected workflow, action, prompt, and execution flag. `server.js` dispatches image, edit, video and upscale work from this plan; workflow-specific decision details remain available. Preserve explicit gate ordering when extending it.
- **Pending clarification state** — removed: video requests no longer ask Direct-video vs Director-mode. See "Director Mode" for the explicit trigger.
- **Two-level intent detection** (still used as signal evidence / fallback in `services/image-generator.js` and `services/video-generator.js`): a fast Level 1 regex SIGNAL (`imageRequestStrength` → `definite`/`likely`/`null`) decides whether the resolver's LLM is consulted; the structured LLM JSON is the final authority on tool execution, the chat model's free-text reply never is. The signal is **not** position-dependent (generation verbs can appear anywhere) and `isConceptQuestion` keeps "What is image generation?"-style questions as chat. Deterministic gates in `task-router.js` (`decisionFromResolvedIntent` excepted) remain only as narrow fallbacks; all classification runs at temperature 0.
- **Extended intent schema**: `detectIntent`/`IMAGE_INTENT_SYSTEM_PROMPT` return/expect `action` (`generate`|`modify`), `creative_mode` (`none`|`light`|`full`), `explicit_constraints`, and chat `related_task`. The resolver mirrors those fields. `CREATIVE_FREEDOM_RE` (exported from `image-generator.js`) detects "be creative"/"surprise me"; a creative request with no subject gets `DEFAULT_CREATIVE_PROMPT`. These fields flow to `buildImagePrompt` and into the ActiveTask `parameters`.
- **SSE streaming** for chat (`/api/chat/stream`) — `queued`/`generating` status, live ComfyUI `progress` (step %), text chunks, `stats`, then a final `done` event; image/video generations emit a single `image`/`video` event. Streamed text is **rendered throttled**: `public/js/chat.js` coalesces chunks into at most one markdown render every ~80ms (trailing edge) and skips the heavy DOM passes (`collapseUpscalePairs`/`VideoPlayer.scan`/card attach) until the final `done`, so a long reply can't saturate the main thread. A running job is cancellable: each `generation-queue` entry owns an `AbortController`, its `signal` is threaded through `withGenerationLock` into `comfyui.waitForPrompt`, and `cancelActive`/`POST /api/queue/cancel {active:true}` aborts the wait and interrupts ComfyUI. The composer stays editable during a stream, queues one follow-up with its conversation ID, and exposes Stop separately; all actual server turns still use the global FIFO for VRAM safety.
- **Restart mechanism**: `POST /api/restart` exits with code `100`, which `start.bat` (Windows) / `start.sh` (macOS/Linux) catches to relaunch in the same terminal. Both launchers preflight for Node.js and offer to install it via `install-node.ps1` (winget → official MSI) or `install-node.sh` (brew/apt/dnf/pacman → official tarball) when missing.

## State-management patterns

- **Server config**: `data/config.json`, managed by `server/config-manager.js` (`getConfig`, `setModelConfig`, `getImageSettings`, `setImageSettings`). The `imageGeneration` key stores global image settings overrides (model, unet, clip, vae, qwenUnet, qwenClip, qwenVae, aspectRatio, imageSize, steps, cfg, qwenSteps, qwenCfg, seedMode, seed, variations, loras; width/height are derived from aspectRatio + imageSize via `resolveDimensions`, unless `imageSize` is `CUSTOM`, in which case the stored `width`/`height` are used directly, clamped to 64–4096 and snapped to the latent grid). Steps/CFG are model-scoped: Krea 2 reads `steps`/`cfg`, Qwen Image 2.1 reads `qwenSteps`/`qwenCfg` (Settings > Image SAMPLING repaints the right pair when the model changes; double-clicking an input resets it to that model's default). `model` selects the active text-to-image pipeline (`qwen_image_2_1` default or `krea2`); `effectiveSettings()` merges defaults with stored overrides, and `resolveBaseModels()` maps the active model to its UNET/CLIP/VAE slots. `seedMode: 'fixed'` + `seed` makes generations reproducible, and `variations` (1–4) emits that many images per request at seed, seed+1, …; the seed used is recorded in generated-history metadata.
- **Conversations/messages**: `data/conversations.json`, managed by `server/conversation-service.js`. In-memory cache reloaded at startup. Conversation memory rolls older turns forward once 20 messages are outside the recent context window; `summaryThroughMessageCount` tracks the covered range. `server/context-builder.js` combines memory with recent history up to 24,000 characters and adds the current user turn once. Users can inspect, edit, or clear memory through the conversation-list memory action (`PATCH /api/conversations/:id { summary }`). A conversation may be flagged `private` (locked) via `PATCH /api/conversations/:id { private }`; the flag hides its generated media from the shared gallery. Each conversation carries a `sessionId` (the owning device session) and API reads/writes are gated by `conversationService.canAccessConversation(id, sessionId)`.
- **Device sessions (per-device privacy)**: every browser gets a long-lived HttpOnly `jarvis_session` cookie, resolved on each request in `server.js` (`resolveSession`, set on the first response — including the HTML document, so it exists before any API call). Conversations, generated media and activity events are scoped to the owning session so a second device on the same WiFi is fully independent. `conversationService.getAllConversations(sessionId)` / `generatedHistory.listPublic(sessionId)` filter by session; `generatedHistory.add` stamps each entry with its conversation's session. Pre-session (legacy) conversations and media have no `sessionId` and are **adopted by the first device that asks** (`adoptLegacyState` → `conversationService.adoptLegacyConversations` + `generatedHistory.adoptLegacy`, idempotent) so an upgrade keeps the existing history on that device. System/VRAM activity events carry no `conversationId` and stay shared. Store paths are env-overridable for tests (`CONVERSATIONS_PATH`, `GENERATED_HISTORY_PATH`, `GENERATED_DIR`, `ACTIVITY_LOG_PATH`)`.
- **Generated media privacy**: image/video metadata entries store the originating `conversationId` and owning `sessionId` (`generated-history.add`). `generatedHistory.listPublic(sessionId)` returns only that session's media and drops entries whose conversation is private; it backs `GET /api/generated` (the gallery widget, View All, and `@` picker). Entries flagged `hidden: true` (the Creative Playground character preview, Character Identity references and dedicated identity base renders, and UGC Studio reference frames) are excluded from `listPublic`/`listRecent` and the ACTIVITY log but stay in `list()` so they can be cleaned up by filename (`removeByFilename`). Internal lookups (`list`) stay unfiltered so deletes/upscale pairing still work; `remove(id, sessionId)` refuses to delete another session's media. Private origins are also skipped by the ACTIVITY log.
- **Active task state**: `data/task-state.json`, managed by `services/task-state.js`. Per-conversation task context (type, prompt, generatedAsset, parameters), reloaded at startup.
- **Generated image metadata**: `data/generated-history.json`, managed by `services/generated-history.js` (cached in memory, flushed on change).
- **LoRA stack**: part of global image settings (`imageGeneration.loras`). Each entry is `{ name, strength, on, triggerWord }`. Trigger words from active LoRAs are prepended to the image prompt at generation time.
- **Frontend settings**: `localStorage` for widget visibility and device settings; IndexedDB for conversations/messages. The last opened conversation is persisted under `jarvis-last-conversation` (managed by `conversations.js`) and reopened on boot by `renderActiveChat` in `app.js`, falling back to the newest conversation if it no longer exists.

JARVIS does **not** reimplement the cache: it integrates the external `duckyshell/ComfyUI-MiniMaxH3-FirstBlockCache` node (`ApplyMiniMaxH3FirstBlockCache`, `MiniMax H3/optimization`, MODEL→MODEL). `buildH3Graph`/`buildLongVideoGraph` call `appendFirstBlockCache(graph, 'model', settings)` **immediately after the diffusion-model loader** so the LoRA chain, Turbo LoRA, attention patch, guider and scheduler all read the patched MODEL; `appendFirstBlockCache` always sends `model`, `mode` and the five manual inputs (`threshold`/`start_percent`/`end_percent`/`max_consecutive_hits`/`temporal_guard`) because ComfyUI requires every required input in the API prompt (the node ignores them outside `Custom — manual values`); the input keys are resolved from ComfyUI `/object_info` via `resolveFirstBlockCacheInputNames` so a renamed field still validates. It is complementary to every attention backend and to Turbo (no artificial incompatibility). Node detection uses ComfyUI `/object_info` (`firstBlockCacheNodeAvailable`); `resolveFirstBlockCacheAvailability`/`assertFirstBlockCacheReady` fail with `h3_fbcache_node_missing` (never silently drops the patch), `validateFirstBlockCache` rejects bad Custom values (`h3_fbcache_invalid`), and `validateH3Graph` rejects duplicates/unconnected output/conflicting cache nodes (`findConflictingCacheNodes`: EasyCache/LazyCache/CacheDiT/T8/double_block). `videoAccelerationInfo`/`formatAccelerationDiagnostics` record mode + attention + Turbo in `generated-history` metadata and the chat reply. Installation mirrors FaceRefine: `services/fbcache.js` (single-flight background job, `getStatus`/`startInstall`/`ensureAutoInstall`, git-clone of `ComfyUI-MiniMaxH3-FirstBlockCache` into `ComfyUI/custom_nodes`; no pip/model step), API `GET /api/video/fbcache/status` + `POST /api/video/fbcache/install`, first-enable auto-install hook in `POST /api/settings/video`. UI: FIRST BLOCK CACHE card in the VIDEO panel with its own Install/check button, status and log (`public/index.html`, `public/app.js` `initVideoSettings`, `.env.example`, README). It is intentionally not part of the Settings > Setup `NODE_CATALOG`.
- **MiniMax H3 Turbo LoRA (4-8 step generation)** - VIDEO setting (`videoGeneration.h3TurboEnabled` / `h3TurboSteps` / `h3TurboLora` / `h3RefTurboLora` / `h3TurboSigmaShift`, env `H3_TURBO_ENABLED` / `H3_TURBO_STEPS` / `H3_TURBO_LORA` / `H3_REF_TURBO_LORA` / `H3_TURBO_SIGMA_SHIFT`), **on by default** — the distilled v4/600-EMA adapter at 6 steps on the model's native canvas is the creator-recommended quality path; set `h3TurboEnabled: false` (or toggle it off in Settings > Video) for the full 25-step base workflow. When on, `buildH3Graph` inserts `MiniMaxH3TurboLoRA` between the user LoRA chain and the attention patch and swaps `KSamplerSelect` for `MiniMaxH3TurboSampler` (from `larryvrh/ComfyUI-MiniMax-H3-Turbo`) while `BasicScheduler` stays on `simple` with the Turbo step count; guider and scheduler both read the Turbo-adapted model. **Reference (ref2va) mode uses a dedicated adapter** (`h3RefTurboLora`, default `minimax_h3_n_turbo_4step_v0.1_comfy_resized_avg_rank_21_bf16.safetensors` from `Kijai/MiniMax-H3_comfy`) — using the frames adapter on the reference model degrades output. **Sigma shift:** for LightX2V standard-loader adapters, `appendH3TurboSigmaShift` optionally inserts the pack's `MiniMaxH3SigmaShift` node (`shift_video: 12` / `shift_audio: 3`, resolved against `/object_info`; no-op when the node is absent) to rebalance the video/audio schedules; the default Frames adapter is not a standard-loader LoRA so no shift is emitted for it. Strength (1.0) and scheduler are fixed and not user-facing. `normalizeH3Turbo(settings, { reference })`/`normalizeH3TurboSteps()` sanitize the setting (4-8 steps, default 6); `assertH3TurboReady(info, settings, { reference })` runs in `generateVideo` and fails (codes `h3_turbo_nodes_missing` / `h3_turbo_lora_missing`, surfaced by `friendlyVideoError`) instead of silently falling back. The LoRA filenames are configurable and discoverable via the existing settings/Setup model config (`services/model-setup.js` `h3_turbo_lora` + `h3_ref_turbo_lora` entries + `h3_turbo` node pack). Turbo applies to both T2V and I2V and only changes the sampling/model path. UI: Turbo card in the VIDEO panel with both LoRA fields (`public/index.html`, `public/app.js` `initVideoSettings`).
- **MiniMax H3 reference-to-video (multi-reference conditioning)** — `buildH3Graph` uses the core `MiniMaxH3ReferenceToVideo` node (ref2va) instead of `MiniMaxH3ImageToVideo` whenever the request carries `referenceImages` (the UGC handoff's approved scene frames). Each frame is uploaded and wired into the node's Autogrow input with the flat dotted keys `ref_images.ref_image_0 … ref_image_8` (**0-based** slots — verified against ComfyUI's `TemplatePrefix` schema; the `<Picture i>` ordinals are 1-based by request order, so `ref_image_0` is `<Picture 1>`), `ref_image_size: 'match'`, and `vae`. No first-frame lock in this mode. `generateVideo` uploads every reference (and deletes them in `finally`), picks the render dimensions from the first frame, and records `mode: 'ref2va'` + `refs` in gallery metadata. **The prompt follows MiniMax's official Full-Reference Mode structure**, not T2VA/I2VA: `H3_REFERENCE_ADDENDUM` overrides the base structure and requires the six sections `subject_definitions` / `summary` / `retention_analysis` / `detailed_description` / `overall_soundscape` / `non_diegetic_music`, with `<Subject N>` for reusable content (defined from the `<Picture N>` sources) and standalone `<Picture N>` only for concrete shot anchors; `buildH3VideoPrompt` rejects a ref reply that lacks `detailed_description` and falls back to the deterministic `buildReferenceFallbackPrompt` (six sections, one `<Picture i>` anchor per shot). The normal (non-reference) H3 path is byte-for-byte unchanged. Tests: `test/video-references.test.js`.
- **H3 dialogue repair (`ensureShotDialogue`)** — the H3 director LLM routinely drops the approved `<d>[Language] …</d>` block, which makes H3 invent speech in its own dominant language (the Mandarin-dialogue bug). `buildH3VideoPrompt` therefore runs `videoGenerator.ensureShotDialogue(prompt, shotPlan, dialogueLanguage)` on every finished prompt: it scopes to the description section (`detailed_description` or `integrated_multimodal_description`, so `[Shot N]` references inside `retention_analysis` are untouched), extracts the authoritative line per shot from the shot plan's `<d>` blocks, replaces any invented/translated `<d>` block in the matching `[Shot N]` with the exact words + language, and appends the line when the block is missing. `parseShotDialogue`/`extractShotDialogues` are exported for tests.
- **First-run setup guide (Settings > Setup)** — backend `services/model-setup.js` (model/node catalogs with verified Hugging Face repo+path per file, streamed HF downloads with the stored `huggingface.token` (`HF_TOKEN`/`HUGGINGFACE_TOKEN` env wins), git-clone node installs, single-flight background job like FaceRefine), API `GET /api/setup/status` + `POST|DELETE /api/setup/token` + `POST /api/setup/download` + `POST /api/setup/install-nodes` + `POST /api/setup/install-ffmpeg` in `server.js`; UI SETUP panel (`public/index.html`, `public/app.js` `initModelSetup` + polling, `.setup-*` in `public/style.css`) covering the Qwen Image 2.1 stack (the default image model, needed for generation and for all image editing), the optional Krea2 image stack, H3 video stack, SeedVR2/Ultimate SD/RTX upscale weights and nodes, the VHS pack, and an OPTIONAL TOOLS card. `status.tools` is backed by `thumbnail.getFfmpegStatus()`; the ffmpeg row offers a one-click background install (`thumbnail.startFfmpegInstall()`, `installPlanFor()` picks winget/brew/apt) with a manual-command fallback and no hard dependency.
- **Settings panel** — `public/index.html` settings markup (GENERAL/SETUP/CHAT/IMAGE/UPSCALE/VIDEO/SYSTEM panels); `public/app.js` `initSettings` / `initModelSetup` / `initImageGenSettings` / `initUpscaleSettings` / `initLoraSettings`.
- **App dialogs** — `public/js/dialog.js` exposes a global `Dialog` (`Dialog.prompt` → `string|null`, `Dialog.confirm` → `boolean`, `Dialog.alert` → `void`) that replaces native `window.prompt`/`confirm`/`alert` with the shared `.modal-*` styling. Markup is `#appDialogOverlay` in `public/index.html`, styles `.dialog-*` in `public/style.css`. Escape/backdrop cancel and Enter-submit are built in.

## Important relationships between components

- **Chat → Image**: In `handleChatStream`, `task-router.routeMessage()` first runs the Intent Resolver (`intent-resolver.resolveIntent`: message + context + signals → structured intent) and maps that intent to an executable decision, then falls back to its own deterministic gates. Only when the decision says `shouldExecuteTool` does the app build a prompt, free VRAM via `vram-manager.freeVRAMBeforeImage()`, and run the pipeline. Otherwise it streams a normal chat reply (after `freeVRAMBeforeChat()`). Prompt meta-requests (`prompt_writing`/`prompt_ideation`) and chat never execute a tool. The router knows three image outcomes: `image_generation` (new T2I), `image_edit` (attached upload, explicit "edit this image", or content-targeted phrasing like "replace X with Y" / "swap X for Y" / "change X into Y" / "remove X" → edit of the upload/latest output via the Qwen editor), and `continue_task`/`modify` (always executed as a full-regen of the rewritten prompt; edits only run for explicit `image_edit`). Deterministic falls back on narrow, explicit intents so small chat models can't downgrade them to chat: upscale (incl. typo-tolerant matching), bare-`again` regenerates, anaphoric `another image`/`one more image` (always a new `image_generation` execution, rebased onto the image lineage by `resolveAnotherImageConcept`), and explicit new-phrasing requests (`isExplicitNewImageRequest` / `VIDEO_REQUEST_RE` — a generation verb driving at a media noun naming a subject). Tweaks, questions, and display requests keep flowing through the resolver/router.
- **Director gate**: in `handleChatStream`, before `taskRouter.routeMessage`, an explicit `body.directorAction` executes a card action, a typed decision matching the open production is classified by `approval-manager.classifyMessage`, and explicit `director mode` phrasing starts a Director production. Every other video request is no longer gated: the Intent Resolver returns `video_generation` with `mode: "direct"` and the normal H3 pipeline runs. A `body.forceDirector` flag from the composer Director Mode toggle hands any fresh `video_generation` decision to `handleDirectorStart` via `director.shouldForceDirector`, bypassing the direct pipeline. When the toggle is on, `director.shouldForceDirectorOverLongVideo` suppresses the Long Video gate first, so a `>15s` request reaches this branch instead of the duration router (a parked long-video plan is removed); `wantsDirectMode` and an actively rendering long video still take precedence. An open production never blocks normal chat: unrelated turns keep flowing through the router.
- **Creative Playground gate**: runs in `handleChatStream` *after* the Director gate and *before* the router/`freeVRAMBeforeChat`. An explicit `body.playgroundAction` (popover Surprise, or a card button) is executed by `handlePlaygroundAction`; a typed follow-up to an untouched preview is classified by `playground.classifyMessage` and enters the same handler. Concept assembly (again/modify/save/use-as-context) is deterministic (no model loads); a new **random character** additionally pre-renders its face via `runPlaygroundFaceStage` (frees VRAM, `buildImagePrompt`, `generateImage`, then `setCharacterImage`) before the card is emitted, failing open. A Surprise with a **saved character** selected (`session.mode === 'character'`) has a known identity, so it skips the preview card and generates the scene immediately (`runPlaygroundGenerate`); random-character and no-character concepts still stop at the card for review. Generate frees VRAM, runs `imageGenerator.buildImagePrompt` on `playground.buildImageRequest`, then `handleImageGenerationStream`. A concept that has been saved/used is no longer "open", so typed follow-ups flow to the normal router and never shadow an active image task.
- **Long video gate**: runs in `handleChatStream` *before* the Director gate (and before the router). An explicit `body.longVideoAction` executes a storyboard action; a typed decision on an open plan is classified by `longVideoDirector.classifyMessage`; a `>15s` video request (`isLongVideoRequest`, raw `parseRequestedSeconds`) starts the Long Video Director and stops at the storyboard approval card. It never reaches the <=15s H3 pipeline. The one exception is the composer Director Mode toggle: with `body.forceDirector` on (`shouldForceDirectorOverLongVideo`, explicit "just generate the video" and an active render still excepted) a `>15s` request bypasses this gate and is handled by the Director above. While a long video is actively rendering, only cancel is honored by the gate — a fresh request flows to the normal router so the running plan state is never clobbered.
- **ActiveTask lifecycle**: per-conversation task state lives in `services/task-state.js` (typed as `image`/`video`/`audio`), persisted to `data/task-state.json`. It stays active across turns and survives server restarts. It is only cleared when the user starts a different non-tool task or the application clears it. Tool execution sets `status: running` before running and `completed`/`failed` only after the tool actually finishes. The task also keeps `lastImage` lineage (prompt, original concept, creative mode) across video tasks so anaphoric requests like "generate me another image" and pronoun upscales rebase onto the image style, never the H3 video prompt; vague lineage prompts ("an image") are skipped in favor of the last concrete one.
- **Image pipeline**: `generateImage()` reads global settings (`effectiveSettings`), prepends active LoRA trigger words to the prompt, builds the Krea2 graph, validates against ComfyUI's object info, queues it, waits, downloads the output, saves to `data/generated/`, and records metadata in `generated-history`.
- **Config flow**: Settings UI → `POST /api/settings/image` → `imageGenerator.saveSettings` → `sanitizeSettings`/`sanitizeLoras` → `config-manager.setImageSettings` → `data/config.json`. At generation time `effectiveSettings()` merges defaults with stored overrides.
- **VRAM orchestration**: `vram-manager` connects chat providers and ComfyUI, unloading whichever model isn't needed to fit the next one in GPU memory.
- **Conversation duplication**: stores exist on both server (`conversations.json`) and client (IndexedDB); they mirror each other for durability.

## Face Action system

- `services/playground/face-actions.js` is a separate data-only vocabulary for coherent facial expression presets and the composable expression / mouth / eyes / head dimensions. It owns weighted theme/Outfit Pack selection, natural-language matching, conflict normalization and prompt formatting; do not fold facial actions into `activities.js` or body pose.
- Playground concepts persist the selected Face Action through card state, the prompt request, generation context and ActiveTask parameters. `concept.js` adds it as a separate facial-expression layer and protects identity attributes; the identity portrait pre-render deliberately omits it. `character-context.js` also structures explicit single-character `@Name` expressions without assigning ambiguous multi-character actions.
- A fresh Surprise may cast a new character. Surprise Me Again keeps the theme and Outfit Pack; random characters are recast unless Identity is explicitly locked, while saved characters remain fixed. It varies scene/pose/camera/automatic Face Action. An explicit Face Action or Face Action lock remains pinned.

## Common entry points for different types of tasks

- **Install reusable H3 references** — Settings > Setup > Custom Nodes includes the optional MiniMaxH3Mod pack, readiness checks for all three nodes, Git install/update, and installation of its Python requirements into ComfyUI's detected interpreter (`COMFYUI_PYTHON` overrides detection). Restart ComfyUI after install. Text-only video remains independent of this pack.
- **Reusable MiniMax H3 visual references** — `services/h3-reference-pipeline.js` owns deterministic semantic reference planning, deduplication, priority/token budgeting, video frame sampling, source hashing, persistent `.safetensors` caching, and the isolated MiniMaxH3Mod ComfyUI adapter. `video-generator.js` prepares optional references and applies cached artifacts through `MiniMaxH3RefModsLoader` → `MiniMaxH3RefModApply` before the shared H3 sampler. A reference-conditioned graph selects the Ref2VA UNET (`H3_REF2VA_UNET` / `H3_UNET_I2VA`); no semantic or native references keeps the existing T2VA graph/settings. Character references use only the approved base portrait (never the multi-panel identity sheet); H3 optimizations remain shared. Explicit character reference failures stop generation rather than falling back to an unrelated render. Debug with `JARVIS_H3_REFERENCE_DEBUG=1`; token budget defaults to 5120 and is configured by `H3_REFERENCE_TOKEN_BUDGET`.

- **Add/change an API endpoint** — `server.js` `handleAPI()`.
- **Change chat behavior/providers** — `server/providers.js`, `server/context-builder.js`, `server/conversation-service.js`.
