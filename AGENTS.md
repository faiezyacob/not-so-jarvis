## Project overview

`not-so-jarvis` is a local AI assistant dashboard ("JARVIS") built with **plain Node.js** (no framework, zero npm dependencies) and **vanilla HTML/CSS/JS** (no bundler). It runs entirely on the user's machine with no cloud dependency. It provides:

- Chat with local AI providers (Ollama)
- System monitoring widgets (CPU, RAM, VRAM/GPU)
- A model library with hardware-compatibility detection
- AI image generation via a local ComfyUI instance using the **Krea2** text-to-image workflow

Version 0.1.0, GPL-3.0-only license. Entry point is `server.js`.

## Purpose of each important directory

- **`server/`** — Server-side application logic. These modules are required by `server.js` and do the actual work: chat, conversations, providers, config, model catalog.
- **`services/`** — Cross-cutting / independent services. `image-generator.js`, `comfyui.js`, and `vram-manager.js` together form the image generation pipeline. `system-monitor.js` provides telemetry, and `weather.js` provides server-side weather lookups for chat. `news.js` parses keyless RSS/Atom feeds for the NEWS widget and chat context. `generated-history.js` persists image metadata and `thumbnail.js` mints the gallery's cached low-res PNG thumbs in the background.
- **`public/`** — Everything served to the browser. `app.js` is the main entry; `public/js/*` are feature modules loaded as plain scripts (no modules/bundler).
- **`data/`** — Runtime persistence. JSON files are the source of truth for config/conversations/history; generated images land in `data/generated/`.

## Important services and integrations

- **Ollama** (`http://localhost:11434`) — chat provider via `server/providers.js`.
- **ComfyUI** (`http://127.0.0.1:8188`, overridable via `COMFYUI_URL`) — image generation via `services/comfyui.js`. Raw ComfyUI failures are classified (`classifyComfyError`) into stable codes (`comfyui_oom`/`comfyui_missing_model`/`comfyui_missing_node`/`comfyui_validation_error`) with actionable hints, and idempotent reads (`getObjectInfo`, `downloadImage`, `/history` polling) use bounded `withRetry` backoff for transient unreachable/5xx errors.
- **ComfyUI launcher** — `services/comfyui-launcher.js` starts a local ComfyUI server as a detached background process when it is offline. Resolution order: an explicit `COMFYUI_START_CMD` (env) or `comfyui.startCommand` (config) override, then ComfyUI Desktop (`installations.json` under the Electron userData dir, launching the standalone install's venv python + `main.py` headless), then a portable/venv layout (sibling `run_nvidia_gpu.bat`/`run_cpu.bat` or a resolved python). `comfyui.root` is cached in `data/config.json` when detected so a launch still works while ComfyUI is offline. `start()` is idempotent and single-flight, writes logs to `data/comfyui-start.log`, and polls `isAvailable()` until `COMFYUI_START_TIMEOUT_MS` (default 180s). Exposed by `POST /api/comfyui/start` (widget Start button) and the deterministic `isStartComfyRequest` chat gate in `handleChatStream` (so a "start comfyui" message never falls through to the chat model). `GET /api/comfyui/status` reports `canStart`/`startMethod` when offline.
- **Krea2 workflow** — assembled in `services/image-generator.js` (`buildKrea2T2IGraph`), using UNET/CLIP/VAE models configured through settings or env vars (`KREA2_*` in `.env.example`).
- **Director Mode** — `services/director/*` coordinates video production. Any new video request stops at a **workflow question** ("Direct video" vs "Director mode") instead of guessing: `director.shouldOfferModeChoice` stages an `awaiting_mode_choice` plan, explicit `director mode` phrasing (`wantsDirectorMode`) goes straight to Director, and explicit "just generate the video" (`wantsDirectMode`) stays on the normal pipeline. Choosing Director builds the canonical brief and runs opening image → approval checkpoint → H3 I2VA video. The canonical creative brief (`production-plan.js`, persisted to `data/director-state.json` per conversation) is the source of truth: a direction change updates the brief via `director-prompts.js` and rebuilds the image prompt, never appends to the old one. The brief has a free-form `details` catch-all (props, wardrobe, dialogue, named styles) so specifics survive the structured fields, and while `briefModified` is false the compose functions also carry the user's original wording as authoritative context for the image/H3 prompts. **Director productions are cut like a film, not one continuous take:** the brief carries an ordered `shotList` (planned by the brief LLM, with `director-prompts.planShots` as the deterministic fallback — roughly one cut per three seconds, capped at five, unless the user explicitly asks for a single take), `composeVideoDirection` translates it into a numbered shot plan, and `buildVideoStageRequest` passes `shot_plan`/`multi_shot` into `videoGenerator.buildH3VideoPrompt`. When a shot plan is present the H3 director switches to the `H3_MULTISHOT_ADDENDUM` (official guide cut syntax: `[Shot N] At 00:0S.SSS, the camera cuts to …`, strictly increasing, no timestamp on `[Shot 1]`), a rewrite with fewer than two `[Shot N]` markers is rejected and retried, and the deterministic `buildMultiShotFallbackPrompt` emits the plan even if every LLM step fails. The normal direct-video pipeline carries no shot plan and stays single-shot unless the user explicitly requests multiple shots. The Director decides WHAT runs; `image-generator.js`/`video-generator.js` decide HOW. The server executes stages through the existing `handleImageGenerationStream`/`handleVideoGenerationStream` by passing `opts.director` (those handlers emit a `director` SSE card instead of the normal `image`/`video` event, mark the production stage ready/failed, and stop at approval); the direct-video choice runs the normal H3 path via `runDirectVideoFromRequest`. Actions arrive as `body.directorAction` on `/api/chat/stream` (button clicks) or as typed decisions (`approval-manager.js` `classifyMessage`); `GET /api/director/state?conversationId=` restores card interactivity after a reload.
- **VRAM manager** — `services/vram-manager.js` enforces "one side resident, always": Ollama and ComfyUI are never loaded at the same time, and there are **no memory-pressure thresholds** (a pre-action check can see a healthy machine while both footprints are already stacked — e.g. right after a generation evicted the chat model but ComfyUI still holds its weights). Before any chat work `freeVRAMBeforeChat` unloads ComfyUI models; `comfyui.queuePrompt` sets a residency flag (`comfyui.hasResidentModels`/`forgetResidentModels`) so it skips the round-trip when the app queued nothing. The free now runs at the **start of the chat turn, before `taskRouter.routeMessage`** (`server.js` `handleChatStream`) because routing and image/video prompt building both consult the Ollama model — waiting until the chat-reply branch would let both load during routing. Before any image/video generation `freeVRAMBeforeImage` unloads **every** model Ollama has loaded (discovered from `/api/ps` via `providerManager.getOllamaStatus`, with `rememberChatModel` as a fallback), so a model loaded outside the app or before a restart is still evicted. The tradeoff is deliberate: a generation unloads and reloads ComfyUI per image/video turn, because prompt building needs Ollama first. `reconcileOnStartup()` (called from `server.listen`) frees ComfyUI models left over from a previous process. Director stages go through `prepareDirectorLlm` before their interleaved Ollama planning calls and `freeComfyModels` at the end of a stage.
- **Open-Meteo weather** — `services/weather.js` fetches current conditions (no API key) for the browser-reported location. The dashboard widget POSTs its geolocation to `/api/weather/location`; the server persists it in `data/config.json` (`weather` key) and injects a gated snapshot into chat context. `GET /api/weather` returns the cached current conditions.
- **RSS news** — `services/news.js` fetches keyless RSS/Atom feeds (curated defaults: BBC World, NPR, Hacker News), parses them with a regex reader (`parseFeed`), and caches the merged items for 10 minutes. The NEWS widget polls `GET /api/news` with a `category` scope (`all`/`global`/`local`) and a segmented ALL/GLOBAL/LOCAL control; `POST /api/news/settings` persists the custom feed list and the `localArea` used by the `local` scope in `data/config.json` (`news` key, sanitized by `config-manager`), resetting feeds to defaults when sent empty. `GET /api/news?topic=…` uses keyless Google News RSS search, and the `local` scope searches the saved area (area + extracted topic). Chat injects a gated snapshot (`buildNewsContext`, `NEWS_QUERY_RE`), with scope from `newsScope` (`LOCAL_NEWS_RE`/`GLOBAL_NEWS_RE`) and a topic from `extractTopic`. Headlines are treated as untrusted data and always link out to the source.

## Chat environment context

- Both chat paths (`handleChat`, `handleChatStream`) call `buildEnvironmentContext(message)` before `contextBuilder.buildContext`, appending a system message with live telemetry (`contextBuilder.buildSystemStatsContext`, gated on `SYSTEM_QUERY_RE`), weather (`weather.buildWeatherContext`, gated on `WEATHER_QUERY_RE`), and news (`news.buildNewsContext`, gated on `NEWS_QUERY_RE`). The gates keep unrelated turns lean, and the prompts instruct the model to use only the supplied values and never invent numbers, a forecast, or headlines. Telemetry now includes GPU utilization (`system-monitor._readVRAM`).

## Important architectural patterns

- **No framework on either side.** Node `http` server + vanilla JS frontend. `server.js` has all routing defined as a sequence of path+method checks inside `handleAPI()`.
- **Service modules exported as plain objects** with named functions; no classes (except `system-monitor.js` which uses a class).
- **Persistence is simple JSON files** in `data/`, rewritten in full on mutation. No ORM/schema library.
- **Frontend mirrors backend persistence**: conversations are also stored client-side in IndexedDB (`public/js/db.js`) for UI durability.
- **Image generation idempotency/locking**: only one image generation at a time, enforced by `withGenerationLock` in `image-generator.js`.
- **Intent Resolver layer (primary decision-maker)** — `services/intent-resolver.js` sits between the user message and the action router: `User Message → Context Builder → Intent Resolver → Structured Intent → Action Router (task-router) → Action`. `resolveIntent()` combines the current message, a compact conversation context (`buildIntentContext`: last user request, last assistant action, last generated image/video, active prompt/generation, parked pending action, selected video mode), explicit wording, and regex signals (`collectSignals`) into a structured intent `{ intent, confidence, mode, requiresClarification, clarificationReason, referencesPreviousContext, referencedGenerationId, extractedRequest, subject, creative_mode, explicit_constraints }`. Intents: `chat`, `image_generation`, `video_generation`, `prompt_writing`, `prompt_ideation`, `modify_previous_generation`, `clarification_response` (+ `image_edit`/`image_upscale`/`video_upscale`). The **action is decided first; media words ("image", "video", "prompt", "portrait", "cinematic") are only subject/context** — "write me a prompt for an image" is `prompt_writing`, not `image_generation`. The resolver NEVER executes a tool; `task-router.decisionFromResolvedIntent()` maps the structured intent to the executable decision. Priority hierarchy: **A** explicit user action ("director mode", "write a prompt …") → **B** pending clarification → **C** conversation references → **D** semantic LLM (final authority when ambiguous, temperature 0, malformed JSON retried once) → **E** regex/keyword signals (evidence only) → **F** chat fallback. Context inheritance is conservative: `referencesPreviousContext` requires a clear reference ("this"/"that"/"her"/"the image"/"make it …"/"change …"), so an unrelated new request never inherits the previous generation. Set `JARVIS_INTENT_DEBUG=1` (or pass `{ debug: true }`) to print the resolver decision, the regex evidence, and the final action.
- **Pending clarification state** — when a video request has no Direct-video vs Director-mode choice (and no source image / established mode), the resolver returns `video_generation` + `mode: "unknown"` + `requiresClarification: true` instead of guessing. `server.js` parks it via `taskState.setPendingAction(conversationId, { intent, mode, request, reason, createdAt })` (`services/task-state.js`, persisted in `data/task-state.json`) and asks the question through the existing Director mode-choice card. The next turn's answer is read by `director.classifyMessage` (or the resolver's `resolveClarificationAnswer`) and resumes the parked request; a clear new request supersedes it. An ambiguous turn keeps it parked — the request is never silently lost.
- **Two-level intent detection** (still used as signal evidence / fallback in `services/image-generator.js` and `services/video-generator.js`): a fast Level 1 regex SIGNAL (`imageRequestStrength` → `definite`/`likely`/`null`) decides whether the resolver's LLM is consulted; the structured LLM JSON is the final authority on tool execution, the chat model's free-text reply never is. The signal is **not** position-dependent (generation verbs can appear anywhere) and `isConceptQuestion` keeps "What is image generation?"-style questions as chat. Deterministic gates in `task-router.js` (`decisionFromResolvedIntent` excepted) remain only as narrow fallbacks; all classification runs at temperature 0.
- **Extended intent schema**: `detectIntent`/`IMAGE_INTENT_SYSTEM_PROMPT` return/expect `action` (`generate`|`modify`), `creative_mode` (`none`|`light`|`full`), `explicit_constraints`, and chat `related_task`. The resolver mirrors those fields. `CREATIVE_FREEDOM_RE` (exported from `image-generator.js`) detects "be creative"/"surprise me"; a creative request with no subject gets `DEFAULT_CREATIVE_PROMPT`. These fields flow to `buildImagePrompt` and into the ActiveTask `parameters`.
- **SSE streaming** for chat (`/api/chat/stream`) — `queued`/`generating` status, live ComfyUI `progress` (step %), text chunks, `stats`, then a final `done` event; image/video generations emit a single `image`/`video` event. A running job is cancellable: each `generation-queue` entry owns an `AbortController`, its `signal` is threaded through `withGenerationLock` into `comfyui.waitForPrompt`, and `cancelActive`/`POST /api/queue/cancel {active:true}` aborts the wait and interrupts ComfyUI.
- **Restart mechanism**: `POST /api/restart` exits with code `100`, which `start.bat` (Windows) / `start.sh` (macOS/Linux) catches to relaunch in the same terminal. Both launchers preflight for Node.js and offer to install it via `install-node.ps1` (winget → official MSI) or `install-node.sh` (brew/apt/dnf/pacman → official tarball) when missing.

## State-management patterns

- **Server config**: `data/config.json`, managed by `server/config-manager.js` (`getConfig`, `setModelConfig`, `getImageSettings`, `setImageSettings`). The `imageGeneration` key stores global image settings overrides (unet, clip, vae, aspectRatio, imageSize, steps, cfg, seedMode, seed, variations, loras; width/height are derived from aspectRatio + imageSize via `resolveDimensions`). `seedMode: 'fixed'` + `seed` makes generations reproducible, and `variations` (1–4) emits that many images per request at seed, seed+1, …; the seed used is recorded in generated-history metadata.
- **Conversations/messages**: `data/conversations.json`, managed by `server/conversation-service.js`. In-memory cache reloaded at startup. A conversation may be flagged `private` (locked) via `PATCH /api/conversations/:id { private }`; the flag hides its generated media from the shared gallery.
- **Generated media privacy**: image/video metadata entries store the originating `conversationId` (`generated-history.add`). `generatedHistory.listPublic()` drops entries whose conversation is private and backs `GET /api/generated` (the gallery widget, View All, and `@` picker); internal lookups (`list`) stay unfiltered so deletes/upscale pairing still work. Private origins are also skipped by the ACTIVITY log.
- **Active task state**: `data/task-state.json`, managed by `services/task-state.js`. Per-conversation task context (type, prompt, generatedAsset, parameters) plus the Intent Resolver's `pendingAction` clarification (`getPendingAction`/`setPendingAction`/`clearPendingAction`), reloaded at startup.
- **Generated image metadata**: `data/generated-history.json`, managed by `services/generated-history.js` (cached in memory, flushed on change).
- **LoRA stack**: part of global image settings (`imageGeneration.loras`). Each entry is `{ name, strength, on, triggerWord }`. Trigger words from active LoRAs are prepended to the image prompt at generation time.
- **Frontend settings**: `localStorage` for widget visibility and device settings; IndexedDB for conversations/messages. The last opened conversation is persisted under `jarvis-last-conversation` (managed by `conversations.js`) and reopened on boot by `renderActiveChat` in `app.js`, falling back to the newest conversation if it no longer exists.

## Development conventions

- **No dependencies.** Do not add npm packages without strong justification; the app is intentionally dependency-free.
- **No comments policy for AI-written code** unless the existing style of the surrounding file includes them (existing code uses `/* === */` block header comments and inline explanations — match that style).
- Follow existing naming and structure patterns when adding features.
- Match the existing "plain functions + `module.exports`" module style on the backend.
- The frontend uses plain global functions and DOM manipulation, not a framework. Feature modules in `public/js/` interact with shared state in `app.js` (e.g., the LoRA stack helpers).
- **Tests:** run `npm test` (Node's built-in `node --test`, zero-dependency). Suites live in `test/` and cover the router/intent classifiers (`routing.test.js`, `intent.test.js`) and the Director (`director.test.js`) with the LLM/storage seams stubbed. Add positive+negative phrase cases here when changing a router regex, a gate, or Director detection/approval.

## Current major features and their locations

- **Intent Resolver** — `services/intent-resolver.js` (structured intent schema, `collectSignals` regex evidence, `buildIntentContext` compact context, `resolveIntent` priority hierarchy, `resolveClarificationAnswer` pending answers, `formatDebugTrace`). Consumed by the action router in `services/task-router.js` (`decisionFromResolvedIntent`). Pending clarifications live in `data/task-state.json` (`services/task-state.js`) and are asked/resumed in `server.js` `handleIntentClarification`/`handlePendingResolution`. Agent-facing overview: see "Intent Resolver layer" under Important architectural patterns.
- **Chat** — `server.js` `handleChat`/`handleChatStream`, `server/providers.js`, `server/context-builder.js`, `server/conversation-service.js`; UI in `public/js/chat.js`, `public/js/conversations.js`, `public/js/db.js`. When an upscaled pair is found, the original image is dropped and only the upscaled image remains (`collapseUpscalePairs`/`setAiContent`), rendered identically to any other chat image (no extra compare container). The original is accessible via the Compare button inside the image's preview lightbox; pair detection keys on the `_up_` filename marker.
- **Suggested-prompt actions** — prompt meta-requests (`prompt_writing`/`prompt_ideation`) render the written prompt in an `md-code-block`; `server.js` `handleChatStream` appends a UI-only `[[prompt-suggestion]]` marker to the saved reply when the resolved intent was prompt writing/ideation and the reply contains a fenced block. `public/js/chat-suggestions.js` (`ChatSuggestions.extract`/`strip`/`attach`, loaded before `chat.js`) strips it for display/speech and attaches "Generate Image" / "Generate Video" cards beneath each `.md-code-block`; clicking fills `#chatInput` with a ready request (nothing auto-sends). `server/context-builder.js` strips the marker from model context like the Director marker.
- **@ image reference picker** — typing `@` in the chat input opens a picker of the current conversation's generated images (`public/js/chat.js` `onChatInput`/`openMentionPopup`/`conversationImages`, scanning rendered `img.md-image` `/generated/` links and enriching prompts from `/api/generated`; arrow/Enter/Escape navigation; markup `#chatMentionPopup` in `public/index.html`, styles `.chat-mention-*`). Selecting one attaches a reference chip rendered in the existing `#chatAttachments` strip (`pendingReference`, `.chat-attachment--reference`/`-badge`) and the send flow appends `![reference](/generated/<file>)` to the persisted user message plus a `references: [filename]` field to `/api/chat/stream`. `server.js` `sanitizeReferenceImage`/`resolveReferenceSource`/`referenceVisionImages` validate it; `task-router.js` reference block routes video wording to `video_generation` I2VA (`resolveVideoMode` explicit-source arg), questions to chat (with the reference as vision), and any other instruction to `image_edit` with `sourceOverride` targeting that exact file.
- **Director Mode** — `services/director/*`; `server.js` `handleDirectorStart`/`handleDirectorModeChoice`/`handleDirectorAction`/`runDirectorImageStage`/`runDirectorVideoStage`/`runDirectVideoFromRequest` + the `director` branch in `handleChatStream`, plus `opts.director` hooks in `handleImageGenerationStream`/`handleVideoGenerationStream`; API `GET /api/director/state`; UI `public/js/director.js` (loaded before `chat.js`) with the persisted `[[director:{...}]]` marker rendered by `chat.js` `setAiContent` and `.director-*` styles. A new video request shows the workflow choice card (`awaiting_mode_choice`) before anything generates; `/api/chat/stream` accepts `body.directorAction` for button clicks (`choose_direct`/`choose_director`/`approve`/`regenerate_image`/`modify_direction`/`cancel`).
- **Image generation (Krea2/ComfyUI)** — `server.js` image intent branch + `handleImageGenerationStream`; `services/image-generator.js`, `services/comfyui.js`, `services/vram-manager.js`.
- **Identity edit (Krea2/ComfyUI)** — instruction-based pixel edits via the Identity Edit LoRA + `comfyui-krea2edit` nodes (`Krea2EditModelPatch`/`Krea2EditGroundedEncode`), adapted from Mix Studio's `krea2-identity-edit.js`. `server.js` `image_edit` branch + `handleImageEditStream`; graph builder `buildKrea2IdentityEditGraph` + `editImage()` in `services/image-generator.js` (single reference, ≤2MP/16px grid, `ref_boost` 4, `grounding_px` 768, Euler/simple, outputs carry the `_edit_` filename marker). Follow-up tweaks of the active image task (`continue_task`/`modify`) always run as a full-regen of the rewritten prompt; identity edits only run for explicit `image_edit` (attached upload, explicit "edit this image" phrasing, or content-targeted phrasing like "replace X with Y" / "swap X for Y" / "change X into Y" / "remove X" via `detectEditIntent`; vague attribute tweaks like "change her dress" stay on full-regen). Meta-talk about the prompt itself ("replace the prompt with ...") is a generation modify, never an edit. Leading conversational filler is stripped from the edit instruction (`cleanEditInstruction`). Settings key `imageGeneration.editLora` (env `KREA2_EDIT_LORA`).
- **Upscaling (shared image + video)** — "upscale this image" routes through `task-router` (`image_upscale` intent) to `handleImageUpscaleStream` → `imageGenerator.upscaleImage`; "upscale this video" routes (`video_upscale` intent via `videoGenerator.detectVideoUpscaleIntent`, checked first) to `handleVideoUpscaleStream` → `videoGenerator.upscaleVideo` (both share the single-generation lock). Images run SeedVR2 or Ultimate SD (an RTX selection falls back to SeedVR2); videos run SeedVR2 or fast RTX (default, an Ultimate SD selection falls back to RTX) — Mix Studio normalization (`seedvr2 ? seedvr2 : rtx`). Source is the last generated image (`resolveUpscaleSource` scans assistant messages for `/generated/<file>`) or video (`resolveVideoUpscaleSource` filters for video extensions, preserving its fps). Both read the ONE shared upscale config (engine, mode, resolution/multiplier, profile, noise, pre-resize, seedvr2 DiT/VAE/attention) in `imageGeneration.*` via `imageGenerator.effectiveSettings()` (`sharedUpscaleSettings()` on the video side); mode/Ultimate SD are image-only, RTX scale/quality are video-only (RTX uses `upscaleMultiplier` as its scale factor). ## Important relationships between components

- **Chat → Image**: In `handleChatStream`, `task-router.routeMessage()` first runs the Intent Resolver (`intent-resolver.resolveIntent`: message + context + signals → structured intent) and maps that intent to an executable decision, then falls back to its own deterministic gates. Only when the decision says `shouldExecuteTool` does the app build a prompt, free VRAM via `vram-manager.freeVRAMBeforeImage()`, and run the pipeline. Otherwise it streams a normal chat reply (after `freeVRAMBeforeChat()`). Prompt meta-requests (`prompt_writing`/`prompt_ideation`) and chat never execute a tool. The router knows three image outcomes: `image_generation` (new T2I), `image_edit` (attached upload, explicit "edit this image", or content-targeted phrasing like "replace X with Y" / "swap X for Y" / "change X into Y" / "remove X" → identity edit of the upload/latest output), and `continue_task`/`modify` (always executed as a full-regen of the rewritten prompt; identity edits only run for explicit `image_edit`). Deterministic falls back on narrow, explicit intents so small chat models can't downgrade them to chat: upscale (incl. typo-tolerant matching), bare-`again` regenerates, anaphoric `another image`/`one more image` (always a new `image_generation` execution, rebased onto the image lineage by `resolveAnotherImageConcept`), and explicit new-phrasing requests (`isExplicitNewImageRequest` / `VIDEO_REQUEST_RE` — a generation verb driving at a media noun naming a subject). Tweaks, questions, and display requests keep flowing through the resolver/router.
- **Director gate**: in `handleChatStream`, before `taskRouter.routeMessage`, an explicit `body.directorAction` executes a card action, a typed decision matching the open production is classified by `approval-manager.classifyMessage`, and explicit `director mode` phrasing starts a Director production. Any other video request is no longer gated by a regex: the Intent Resolver returns `video_generation` + `mode: "unknown"` + `requiresClarification` when the workflow is unspecified, and `handleIntentClarification` parks the request (`taskState.setPendingAction`) and shows the Direct-video-vs-Director-mode card. An open production never blocks normal chat: unrelated turns keep flowing through the router.
- **ActiveTask lifecycle**: per-conversation task state lives in `services/task-state.js` (typed as `image`/`video`/`audio`), persisted to `data/task-state.json`. It stays active across turns and survives server restarts. It is only cleared when the user starts a different non-tool task or the application clears it. Tool execution sets `status: running` before running and `completed`/`failed` only after the tool actually finishes. The task also keeps `lastImage` lineage (prompt, original concept, creative mode) across video tasks so anaphoric requests like "generate me another image" and pronoun upscales rebase onto the image style, never the H3 video prompt; vague lineage prompts ("an image") are skipped in favor of the last concrete one.
- **Image pipeline**: `generateImage()` reads global settings (`effectiveSettings`), prepends active LoRA trigger words to the prompt, builds the Krea2 graph, validates against ComfyUI's object info, queues it, waits, downloads the output, saves to `data/generated/`, and records metadata in `generated-history`.
- **Config flow**: Settings UI → `POST /api/settings/image` → `imageGenerator.saveSettings` → `sanitizeSettings`/`sanitizeLoras` → `config-manager.setImageSettings` → `data/config.json`. At generation time `effectiveSettings()` merges defaults with stored overrides.
- **VRAM orchestration**: `vram-manager` connects chat providers and ComfyUI, unloading whichever model isn't needed to fit the next one in GPU memory.
- **Conversation duplication**: stores exist on both server (`conversations.json`) and client (IndexedDB); they mirror each other for durability.

## Common entry points for different types of tasks

- **Add/change an API endpoint** — `server.js` `handleAPI()`.
- **Change chat behavior/providers** — `server/providers.js`, `server/context-builder.js`, `server/conversation-service.js`.
- **Change task/intent routing or ActiveTask lifecycle** — `services/intent-resolver.js` (semantic intent), `services/task-router.js` (action routing + `decisionFromResolvedIntent`), `services/task-state.js`, `server.js` `handleChatStream` + `handleImageGenerationStream`.
- **Change Director Mode / multi-stage productions** — `services/director/*`, the director branch in `server.js` `handleChatStream`, the `opts.director` hooks in the image/video stream handlers, and `public/js/director.js`.
- **Change image generation / prompt / LoRA logic** — `services/image-generator.js`.
- **Change ComfyUI communication** — `services/comfyui.js`.
- **Change VRAM/unload orchestration** — `services/vram-manager.js`.
- **Change system telemetry** — `services/system-monitor.js`.
- **Change UI/UI logic** — `public/index.html`, `public/app.js`, `public/js/*`, `public/style.css`.
- **Change persisted settings schema** — `server/config-manager.js` (storage) + the relevant `sanitize*` in `services/image-generator.js` (or other service).
- **Add/remove a catalog model** — `server/models.js`.
